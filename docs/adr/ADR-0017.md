# ADR-0017: 값 검증은 계층이다: 형식(계약) -> 의미(turn-engine) -> 값 타당성(서비스)

## 상태
승인(D75, 2026-10-27), 값 타당성 계층은 감사 TE-1 대응(D88)

## 맥락
모델 출력이 형식은 맞아도 의료 기록에 틀린 값을 넣을 수 있다. 값을 지어내 저장하면 안 된다.

## 결정
1) 모델 서버가 출력 형식을 보장(스키마 제약, 끝내 못 지키면 503 OUTPUT_INVALID). 2) 서비스가 turn-engine `validate_extraction`과 `check_slots`로 의미·칸 존재를 검증, 위반이면 같은 요청을 1회 재시도, 그래도면 그 턴을 NOT_COMMITTED로 하고 세션 상태는 바꾸지 않는다(D75). 3) `check_values`: 현재 문항(또는 next_item과 같은 계열, 현재 문항에서 next_item까지의 문항) 밖 칸 저장 거부(정정 제외), 값 형식·크기(숫자 100만 이하, 문자열 200자 이하), 슬롯 정의가 아는 타입(선택지, 예/아니오, 단위), 이미 저장된 값과 같은 종류.

## 왜 (따른 표준과 근거)
표준: 입력 검증을 경계마다 두는 심층 방어, 모델 출력은 신뢰하지 않는다. 근거 출처: DECISIONS.md D75, 감사 model-runtime-turn-engine.md TE-1(재현 사례). **한계**: QuestionBank의 칸에 값 타입 필드가 없어 처음 쓰는 자유 칸의 타입은 알 수 없고(CR-017 제안), 숫자 상한 100만과 문자열 200자는 근거 기록 없음(거친 타당성 상한).

## 검토한 대안과 버리는 이유
turn-engine에만 맡기기: 값 타당성·타 문항 덮어쓰기를 안 본다(TE-1). 모델이 틀리면 되묻기만: 틀린 값이 저장된 뒤에는 늦다.

## 결과
얻는 것: 틀린 값이 기록에 들어가지 않는다. 감수하는 것: 정상 답도 규칙에 걸려 NOT_COMMITTED가 될 수 있다(되묻기로 이어짐). 규칙이 문항 흐름 계열 가정(Q4와 Q4_1)에 의존한다.

## 되돌리는 조건
문항 세트에 칸 값 타입 필드가 생기면 추측 규칙을 그것으로 대체한다.

## 학습 데이터 대조 결과 (2026-10-28)
C1 학습 데이터 A 정답 32,170행으로 이 계층을 시험해 정상 정답 2행을 잘못 거부한 것을 찾아 규칙을 고쳤고(한 발화가 여러 문항을 채우고 next_item이 END), 고친 뒤 거부 0행이다. 선택지·단위 규칙은 이 데이터와 시험용 문항 세트로 시험하지 못했다(boundary.md 참조).
