# ADR-0005: 한 턴의 오케스트레이션은 LangGraph StateGraph이다

## 상태
승인(D62, 2026-10-15 사용자 지시)

## 맥락
한 턴은 분기(처리 표, 위험, 실패, 흐름 종료)가 많고, 쓰기 확정 전·후의 규칙(확정 뒤에는 앞 단계로 돌아가지 않는다)을 코드 구조로 드러내야 한다.

## 결정
`graph.py`가 `StateGraph`로 노드(선별, 읽기, 추출, 검증, 계획, 확정, 직원 전달, 응답, 종료)와 간선을 정의한다. 체크포인터·병렬 가지는 쓰지 않고, 자원(저장소, 릴리스, 엔진)은 상태 밖에 둔다.

## 왜 (따른 표준과 근거)
표준: 상태 기계를 명시적 그래프로 표현하는 것. 근거 출처: DECISIONS.md D62(사용자 지시: 분기 처리가 쉬워진다), docs/design.md §14·§16, `tests/test_graph.py`가 노드·간선을 설계와 대조한다. 버전은 `requirements.lock`에 고정하고 이미지 라벨 `io.openit.langgraph`에 기록한다.

## 검토한 대안과 버리는 이유
손으로 쓴 if/else 오케스트레이터(D62 이전의 구현): 분기가 늘수록 읽기 어렵다는 것이 사용자 지시의 이유였다. 다른 워크플로 엔진: 근거 기록 없음(사용자 지시가 LangGraph를 지정).

## 결과
얻는 것: 분기와 순서가 시험으로 검증되는 그래프. 감수하는 것: langchain-core 등 의존 증가, 잠금 파일 관리, 라이브러리 버전과 시험(`test_langgraph_is_pinned_in_lock_and_matches_installed`)의 결합.

## 되돌리는 조건
LangGraph 의존의 보안·유지 부담이 이점을 넘거나(이 라이브러리가 추적 기능을 끄는 환경 변수가 필요한 점 포함), 그래프가 단순해져 상태 기계 직접 구현이 더 작을 때.
