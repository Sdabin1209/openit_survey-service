# ADR-0003: psycopg3 직접 사용, ORM 없음, 연결 풀 없음

## 상태
승인(D85 2단계), 풀 없음은 측정으로 재확인(boundary.md §6-1)

## 맥락
저장소 SQL은 SQLite와 같은 본문을 공유하고(`?` 자리표시를 `%s`로 바꾼다), 문서(JSON) 한 줄 읽고 쓰는 단순한 접근이다.

## 결정
`psycopg[binary]==3.3.6`을 직접 쓴다(libpq 내장 wheel). 저장소마다 연결 하나를 락으로 보호한다(`PgConn`). ORM·연결 풀은 쓰지 않는다. 접속 문자열은 모듈 밖으로 내지 않는다.

## 왜 (따른 표준과 근거)
표준: 드라이버 직접 사용은 SQL이 작고 고정일 때의 관행, psycopg3는 현행 표준 PostgreSQL 드라이버. 풀 없음의 근거(측정, 이 PC·가짜 모델): PostgreSQL 연결은 동시 100 세션에서도 3개로 일정했고, 처리량은 연결이 아니라 파이썬 프로세스의 CPU 한계(약 12~14 턴/초)에서 포화했다(boundary.md §6-1, CPU 시간 9.4초 / 벽시계 9.7초). 근거 출처: docs/CHANGELOG.md 'D85 2단계', boundary.md §6-1.

## 검토한 대안과 버리는 이유
SQLAlchemy 등 ORM: SQL 본문을 두 방언이 공유하는 구조에 계층이 하나 더 생긴다(근거 기록 없음, 표준은 ORM이므로 규모가 커지면 재검토). psycopg_pool 연결 풀: 병목이 연결이 아님을 측정했고, 문서 한 줄을 쓰는 짧은 트랜잭션이라 이점이 작다.

## 결과
얻는 것: 단순한 코드, 접속 문자열 비노출을 한 곳에서 지킨다. 감수하는 것: 저장소 연결 하나에 락 직렬화(같은 저장소 쓰기는 한 번에 하나), 프로세스를 늘리지 않으면 처리량이 늘지 않는다.

## 되돌리는 조건
실제 LLM 지연을 포함한 측정에서 DB 대기가 병목으로 나오거나, 프로세스 복제 시 PostgreSQL 연결 수 한도에 닿을 때.
