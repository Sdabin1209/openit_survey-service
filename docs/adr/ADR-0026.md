# ADR-0026: 모델 호출별 상한 extract 3.0초·respond 2.0초와 예산 기반 재시도 (점검 F03)

## 상태
승인(헤드 결정표 2026-10-29 단계 B, 계약 2.2.0 CONVENTIONS.md 표). 값은 **측정하지 않았다**.

## 맥락
한 환자 턴은 모델을 두 번 부른다(extract, 이어서 respond). 이전 설정은 호출 하나당 4초·재시도 1회·백오프 0.2초(지터 없음)였다(점검 F03, ADR-0025 표). 최악은 4+4=8초로 서버 턴 마감 6초(ADR-0008)를 넘어, 호출별 timeout의 합이 마감을 넘는 구조였다.

## 결정
- 호출별 상한: `SURVEY_INFERENCE_EXTRACT_TIMEOUT_SECONDS` 3.0, `SURVEY_INFERENCE_RESPOND_TIMEOUT_SECONDS` 2.0. 종류마다 별도 HTTP 클라이언트로 상한을 건다(`remote.py`). `SURVEY_INFERENCE_TIMEOUT_SECONDS`(4.0)는 제어 호출(릴리스 적재 확인, readyz)에만 쓴다.
- 재시도는 **남은 턴 예산이 그 호출의 상한 이상일 때만** 한다. 남은 예산 = 턴 마감(`time.monotonic` 기준, graph가 `deadline=`으로 넘김) - 지금 - 백오프 대기. 모자라면 재시도하지 않고 실패로 둔다(`retry_skipped_budget`로 센다). 턴 마감을 끈 구성(deadline 없음)은 횟수 제한(`SURVEY_INFERENCE_RETRIES`, 1)만 본다.
- 타임아웃은 이전처럼 재시도하지 않는다(서버가 바쁘다는 뜻이라 지연만 두 배가 된다). 백오프 0.2초×회차(지터 없음)는 그대로다.

## 왜
- 출처는 계약 `CONVENTIONS.md`의 시간 사슬 표(2.2.0)다: "호출별 상한의 합(5.0초)에 서버 처리 여유 1.0초를 더해 턴 마감 6초 안에 들어온다", "재시도는 남은 턴 예산이 호출 상한 이상일 때만". 표준 이름이 있는 규칙이 아니다. 요청 전체에 마감을 걸고 안쪽 timeout을 그 안에 배분한다는 일반 원칙(deadline propagation)을 따른다.
- **3.0/2.0 배분은 측정하지 않았다.** 근거는 합 5.0 + 여유 1.0 = 6.0이라는 산수뿐이고, 실제 LLM 지연(H1 GPU)은 측정 전이다. 실제 지연이 길면 정상 턴도 timeout으로 NOT_COMMITTED가 된다(재전송으로 복구, ADR-0008과 같은 감수).
- 백오프를 예산에서 빼는 것은 재시도가 상한을 지키게 하려는 선택이다(내 판단, 계약에 없음).

## 검토한 대안과 버리는 이유
- 호출별 상한을 그대로 두고 턴 마감에만 맡기기: 마감이 호출을 끊지 못해(ADR-0008 '감수') 느린 extract가 respond 몫까지 쓴다.
- 남은 예산이 있는 만큼으로 호출 timeout을 줄이기(`min(상한, 남은 예산)`): 더 촘촘하나 계약이 정한 규칙이 아니고 호출이 짧게 끊겨 정상 응답을 버릴 수 있다. 하지 않았다.
- 재시도 시 남은 예산에서 이후 호출(respond) 몫을 미리 빼기: 계약 문구보다 엄격하다. extract가 2.9초에 비타임아웃 오류로 실패하면 남은 3.1초로 재시도가 가능해 respond 몫이 없을 수 있다(턴 마감이 NOT_COMMITTED로 끊는다). 이 경우는 드물다고 보고 계약 문구를 그대로 따랐으며 발생 빈도는 측정하지 않았다.

## 결과
얻는 것: 정상 최악 경로가 3.0+2.0=5.0초로 마감 6초 안에 들어온다(시험이 실제 시간으로 확인). 감수하는 것: 위 한계, 값이 잠정이다.

## 되돌리는 조건
GPU 실측(H1)으로 값을 재정한다. 계약 표가 바뀌면 맞춘다.
