# ADR-0045: 문항 은행의 적재 거부 조건을 문진 스키마로 옮기고, 칸 규격은 적재에서 계약으로 검증한다

## 상태
승인(헤드 지시 wo-320, 독립 검토 결과). ADR-0043의 `MISSING_FIELD_SPEC` 적재 검사와 감사 I3의 `MISSING_FIXED_SENTENCE` 검사를 대체한다. 문진 스키마 3.0.0(깨지는 변경) 후보. 스키마 태그는 헤드가 만든다.

## 맥락
독립 검토가 세 가지를 찾았다. 사실 확인(이 세션에서 코드를 읽은 것): (1) 문진 스키마 `SlotDef`는 `choice_catalog`가 있으면 `choices`를 비우게 하는데(`allOf if/then maxItems 0`), `fields.py`는 `choices`만 봐서 catalog로 낸 option 칸은 `MISSING_FIELD_SPEC`으로 거부됐다. question-authoring이 catalog로 내는지는 이웃 코드라 읽지 못했다(헤드가 알려 준 내용이다). (2) 필수 고정 문장 4개, 칸 `data_type`, option 선택지는 적재에서만 거부돼 생산자와 게이트가 미리 못 잡았다. (3) 문진 스키마는 ID에 `minLength 1`뿐인데 계약 `QuestionFieldSpec.slot`은 패턴(`^[A-Za-z0-9_.]+\\.[A-Za-z0-9_]+$`)과 `options`·`repeat_keys` `uniqueItems`를 요구해, 적재는 되고 extract가 400이 되는 은행이 가능했다.

## 결정
1) `fields.option_codes(slot)`: `choice_catalog`가 있으면 각 `code`, 없으면 `choices`. `build_field_specs`와 검사가 같은 함수를 쓴다.
2) 스키마로 표현할 수 있는 거부 조건은 `QuestionBank.json`으로 옮긴다: 필수 고정 문장 4개(`allOf` 안 `contains`, 문장은 `\\S` 포함), 슬롯 `data_type` 필수, `data_type=option`이면 `choices`가 비어 있지 않거나 `choice_catalog`가 있어야 함, `QuestionId` 패턴 `^[A-Za-z0-9_.]+$`, `slot_id` 패턴 `^[A-Za-z0-9_]+$`, `choices` `uniqueItems`. 스키마로 표현할 수 없는 것(`choice_catalog` 코드 중복)은 스키마 설명에 "적재 거부 조건"으로 적었다.
3) 적재는 스키마를 먼저 본다(`INVALID_RECORD`, 문구에 위반 위치와 스키마 설명). 이어서 `invalid_field_specs`가 만든 칸 규격을 계약 `QuestionFieldSpec`으로 검증해 어기면 `INVALID_FIELD_SPEC`으로 거부한다(스키마와 계약 사이 어긋남을 마지막 문에서 잡는다).
4) 적재의 옛 손 검사(`missing_field_specs`, 필수 고정 문장 검사)는 지운다. 같은 규칙을 코드와 스키마 두 곳에 두면 어긋난다. 코드 `MISSING_FIXED_SENTENCE`, `MISSING_FIELD_SPEC`은 없어진다.
5) 문진 스키마 패키지 버전 2.0.0 -> 3.0.0.

## 왜
- 표준: JSON Schema가 표현할 수 있는 제약은 스키마에 둔다. 생산자(question-authoring)와 게이트가 같은 스키마로 미리 검증해 적재에서야 실패하지 않게 한다. 구조 규칙 5, 6과 R7(스키마가 보증한 값을 받는 쪽이 다시 검증하지 않는다)에 맞는다.
- 계약 검증을 적재에 두는 이유: 칸 규격 모양은 계약이 정본이다. 스키마에 패턴을 복사해 두면 어긋날 수 있으므로 적재가 계약 자체를 본다.
- MAJOR인 이유: 스키마만 보고 은행을 만들던 쪽의 기존 은행(예: `data_type` 없음)이 무효가 된다. 서비스 적재는 이미 그런 은행을 거부하고 있었으므로 **적재되던 은행이 새로 거부되지는 않는다**(이 세션에서 시험으로 확인: 시험용 은행 sample_bank 52칸 통과). 엄격한 SemVer는 기존 유효 문서를 무효로 만드는 변경을 MAJOR로 본다.

## 검토한 대안과 버리는 이유
- 로더 손 검사만 고친다(스키마 불변): 생산자와 게이트가 계속 미리 못 잡는다. 지시(2)에 반한다.
- MINOR(2.1.0)로 낸다: 적재 결과가 같다는 점에서는 맞지만 스키마 검증만 쓰는 이웃에는 깨지는 변경이다. 이웃 영향을 숨기게 된다. 버린다.
- 스키마와 손 검사를 둘 다 둔다: 중복이고 어긋난다. 버린다.
- ID 패턴을 스키마에 넣지 않고 적재만 본다: 생산자가 미리 못 잡는다. 계약 패턴을 스키마에 같이 적고, 적재는 계약으로 마지막 확인한다.

## 결과
얻는 것: catalog 은행이 적재된다. 거부 조건이 한 곳(스키마)에 있다. extract가 400이 될 은행이 적재 때 거부된다. 감수하는 것: (1) 적재 거부 코드가 바뀐다(`MISSING_FIXED_SENTENCE`, `MISSING_FIELD_SPEC` -> `INVALID_RECORD`/`INVALID_FIELD_SPEC`). 이 코드를 읽는 이웃이 있는지는 읽지 못했다(운영 화면, 게이트 등은 헤드가 확인). (2) 오류 문구가 스키마의 첫 위반 하나와 설명이어서 옛 문구보다 덜 구체적일 수 있다(위반 건수를 함께 낸다). (3) 영향 영역: question-authoring(생산자, 모든 슬롯에 `data_type`·선택지, ID 문자), release-gate(QuestionBank 스키마 검증 쪽), 문진 스키마 3.0.0을 고정하는 모든 영역과 deploy 버전 기준표(이미지 라벨 `io.openit.contracts.survey-schema`가 `3`이 된다). 이웃 코드는 읽지 못해 영향의 실제 크기는 확인하지 않았다.

## 되돌리는 조건
이웃이 새 거부 코드를 읽지 못해 운영에 문제가 되면 코드 이름만 옛 것으로 되돌린다. 스키마 규칙은 유지한다.
