# ADR-0006: 세션은 문서(JSON) 한 줄과 정수 revision으로 저장한다

## 상태
승인(설계 당시부터)

## 맥락
세션 상태의 모양은 문진 스키마(계약)가 정하고, 서비스 내부 정보를 계약 문서에 섞으면 스키마를 어긴다. 한 턴의 쓰기는 문서 전체의 일관된 갱신이다.

## 결정
`sessions(session_id, revision, doc)`에서 doc은 계약 문서를 TEXT(JSON)로 저장하고, 낙관적 revision 검사와 PostgreSQL의 행 잠금(`FOR UPDATE`)으로 충돌을 막는다. 릴리스 바인딩·턴 결과 같은 내부 정보는 별도 테이블에 둔다.

## 왜 (따른 표준과 근거)
표준: 계약 문서를 그대로 저장하는 문서 모델과 낙관적 동시성 제어(버전 열). 근거 출처: docs/design.md §6 '[결정]'. SQLite와 PostgreSQL이 바이트까지 같은 JSON을 쓴다(CHANGELOG 'D85 2단계').

## 검토한 대안과 버리는 이유
정규화된 관계형 테이블(답·기록을 행으로): 계약 문서와의 변환이 늘고 스키마 변경마다 마이그레이션이 필요하다(근거 기록 없음, 질의 요구가 늘면 재검토). PostgreSQL JSONB: 질의는 쉬워지나 SQLite와 본문을 공유하기 어렵다.

## 결과
얻는 것: 계약과 저장 모양이 같다, 두 DB가 같은 코드. 감수하는 것: 문서 전체를 매 턴 다시 쓴다(세션이 길면 쓰기량 증가, 점검 G3), 세션 내부 질의(예: 모든 세션의 특정 답 조회)가 어렵다.

## 되돌리는 조건
세션 문서가 커져 쓰기 비용이 문제가 되거나, 서비스가 세션 내부를 질의해야 하는 요구(통계 등)가 생길 때.
