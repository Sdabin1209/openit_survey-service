# ADR-0067: survey-db 이미지는 postgres 사용자(uid 999)로 실행한다

## 상태
승인(헤드 지시 2026-11-08, 대장 #8). ADR-0063(survey-db 이미지)의 실행 사용자를 바꾼다(root 시작 -> postgres).

## 맥락
이미지에 `USER`가 없어 진입점이 root(uid 0)로 시작해 인증서·비밀을 postgres 소유로 복사하고 `gosu`로 내려갔다. 공통 규칙은 "root가 아닌 사용자로 실행한다"이다. 주입 선언 `db/inputs.json`도 uid 0과 능력 5개(CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID)를 선언하고 있었다.

## 결정
- Dockerfile에 `USER postgres`(공식 이미지의 uid 999, gid 999)를 둔다.
- 진입점은 postgres로 시작하므로 `install`의 소유자 지정과 `gosu`를 없앤다. 복사한 인증서·비밀 사본은 이 프로세스 소유(0600)다.
- `db/inputs.json`: process 999:999, writable 3곳의 `written_by` 999:999, `capabilities` 빈 목록.
- 공식 entrypoint는 root가 아니면 gosu·chown 없이 그대로 initdb한다(공식 이미지 문서의 "arbitrary --user" 경로). 데이터 폴더(이미지의 VOLUME)는 이미지가 postgres 소유로 만든다.

## 왜
- 공통 규칙, 그리고 최소 권한(CIS Docker Benchmark 4.1: 컨테이너 사용자는 root가 아니어야 한다).
- build-image.sh의 선언 대조가 이미지 실행 사용자(`id -u`)와 선언 process를 비교한다. 둘이 같아야 배치 쪽이 선언의 uid로 파일·쓰기 권한을 준다.

## 검토한 대안과 버리는 이유
- root 유지(능력만 제한): 규칙 위반이고 진입점 복사 단계가 root 권한에 기대는 구조가 남는다.
- 다른 uid(예: 10001): 공식 이미지의 데이터 폴더·소켓 소유가 postgres(999)라 chown 단계가 다시 필요해진다.

## 결과
- 얻는 것: root 없는 실행, 능력 없음, 선언과 이미지 일치(시험이 고정).
- 감수하는 것: 배치 쪽이 `/run` tmpfs와 비밀·인증서 읽기 권한을 uid 999에 맞춰 줘야 한다(선언 written_by·files가 그 약속). 이 영역 시험은 `--tmpfs /run:uid=999`와 읽기 가능한 비밀로 모사한다. 실제 deploy 배치에서의 기동은 이 영역이 확인하지 못했다.

## 되돌리는 조건
공식 이미지가 postgres 사용자(uid)를 바꿀 때(선언과 대조 시험이 알린다).
