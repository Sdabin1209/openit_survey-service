# ADR-0032: 연속 상한은 REDIRECT와 실패 턴도 센다 (U34)

## 상태
승인(헤드 지시 OPEN_GAPS U34, 결함 수정). ADR-0020의 반복 정의를 넓힌다. 상한 값(기본 3)과 정지 방식(직원 호출, PAUSED_RISK, CALL_STAFF 알림, 고정 문장)은 바꾸지 않는다.

## 맥락
ADR-0020은 REASK·CONFIRM만 연속으로 셌다. REDIRECT는 연속을 끊었고, 실패한 턴(NOT_COMMITTED)은 끊지도 세지도 않았다. 그래서 모델이 REDIRECT만 내거나 추출·검증이 계속 실패하면 서버는 직원을 부르지 않았다(키오스크 화면의 실패 3번 호출만 남는다).

## 결정
1) 연속에 세는 것: REASK, CONFIRM, REDIRECT로 확정(COMMITTED)된 턴, 그리고 추출(LoRA-A)·검증(VALIDATE) 단계에서 끝내 실패한 턴(마감 초과 포함). NEXT·CORRECT·HOLD·SKIP, 재개·시작은 연속을 끊는다. 그 밖의 실패(확정 실패, 응답 생성 실패)와 무시된 턴은 전과 같이 끊지도 세지도 않는다.
2) 이번 턴이 REASK·CONFIRM·REDIRECT이거나, 추출·검증이 실패했고 앞선 연속이 상한 이상이면 같은 직원 호출 경로를 탄다. 실패한 턴은 출력이 없으므로 합성 REASK(현재 문항, 값 없음)를 `plan_writes`로 보내 기존 경로를 그대로 쓴다. 이 합성 출력은 대화 로그에 REASK로 남고 입력원(RiskSource)에는 보여 주지 않는다. 턴 마감을 이미 넘긴 실패 턴은 확정할 시간이 없어 실패로 두고 다음 연속에 센다.
3) 멱등: 실패한 턴은 확정 기록이 없어 같은 turn_id로 다시 올 수 있고, 올 때마다 대화 로그에 항목이 쌓인다(턴 결과를 고정하지 않는 CR-D25). 로그 항목에는 turn_id가 없어(로그 항목 스키마 `additionalProperties:false`, 바꾸려면 문진 스키마 변경) 세션 시각 기록(`session_timeline`: 로그 위치 -> turn_id)으로 같은 turn_id를 한 번만 센다. 시각 기록을 읽을 수 없으면 거르지 않는다(직원을 더 일찍 부르는 쪽이 안전하다). 확정된 턴은 저장된 결과를 재생하므로 두 번 세지 않는다.

## 왜
상한이 막으려는 것은 환자가 진전 없이 같은 자리에 머무는 것이다. REDIRECT(주제 이탈)와 모델 실패도 진전이 없다는 점에서 REASK와 같다. 새 정지 경로나 문구를 만들지 않고 이미 시험된 경로를 재사용한다(ADR-0020). 값 3은 그대로이고 측정하지 않았다. 실제 모델이 REDIRECT를 정상 흐름 중에도 자주 내는지는 확인하지 못했다(학습 데이터가 단일 턴). 그렇다면 직원 호출이 늘 수 있다.

## 검토한 대안과 버리는 이유
실패 턴마다 대화 로그가 아닌 별도 카운터 열: 저장소 스키마(마이그레이션) 변경이 필요하고 로그와 어긋날 수 있다. 로그 항목에 turn_id 추가: 문진 스키마 변경과 태그가 필요하다. 실패 턴을 도중에 합성 출력 없이 직접 정지: 확정·알림·응답 경로를 두 번 만들게 된다.

## 결과
얻는 것: REDIRECT만 이어지거나 모델이 계속 실패해도 직원이 호출된다. 감수하는 것: (1) 합성 REASK가 로그에 REASK로 남는다(추적상 extract_status는 ERROR/VIOLATION 그대로). (2) 시각 기록이 없는 구성(저장소를 직접 쓰는 시험 등)에서는 재전송 실패가 중복으로 센다. (3) 로그 항목 수 N(1000자)와 무관하게 읽기가 한 번 더 늘어난다(세션 시각 기록 조회, 호출은 연속 판정이 필요한 턴에만).

## 되돌리는 조건
정상 대화에서 REDIRECT가 자주 나와 직원 호출이 과하면 REDIRECT를 세지 않거나 값을 올린다(헤드 결정). 로그 항목에 turn_id가 생기면 시각 기록 조회를 지운다.
