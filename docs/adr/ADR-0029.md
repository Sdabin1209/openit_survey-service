# ADR-0029: HTTP 서버는 WSGI(PEP 3333) 앱 + waitress이다

## 상태
승인(헤드 결정 D111, 2026-10-29). ADR-0004(표준 라이브러리 ThreadingHTTPServer)를 대체하고, ADR-0018의 소켓 읽기 제한·접속 상한 직접 구현을 대신한다(웹 푸시 SSRF 차단은 그대로).

## 맥락
ADR-0004는 표준 라이브러리 서버를 쓰는 이유를 "의존 최소"로 적었으나 실제 의존(langgraph 등)과 맞지 않았고, slowloris 방어·접속 상한·종료 처리를 직접 구현했다(표준 점검 B01·B02). 프로덕션 서버를 쓰는 것이 표준이다.

## 결정
`survey_service/service.py`의 `make_wsgi(app)`가 WSGI 애플리케이션이고, 서버는 `waitress.create_server`(단일 프로세스, 다중 스레드)이다. 직접 만든 `ThreadingHTTPServer` 하위 클래스, 접속 상한 세마포어·503 쓰기, 소켓 읽기 제한 코드를 지웠다. 설정과 값의 출처:

| waitress 설정 | 값 | 출처 |
|---|---|---|
| threads | 처리 중 요청 상한(`api_max_inflight` 32) + SSE 상한(50) + 4 | 제약: SSE 스트림은 끝날 때까지 작업 스레드 하나를 쥔다. 두 상한이 동시에 차도 `/healthz` 같은 요청이 설 자리가 남아야 한다. 32와 50은 기존 설정(측정: boundary.md §6-1, 측정 안 함: ADR-0018), +4는 근거 기록 없음 |
| connection_limit | `SURVEY_MAX_CONNECTIONS`(256) + 2 | 기존 설정(측정 안 함). +2는 제약: waitress가 듣기 소켓과 깨우기 소켓을 센다. 측정으로 확인(limit=4에서 응답한 동시 연결 2개) |
| channel_timeout | `SURVEY_SOCKET_TIMEOUT_SECONDS`(15)를 올림한 정수 초 | 기존 설정(측정 안 함). waitress 값은 정수 초 |
| cleanup_interval | 1초 | 제약: 기본 30초면 channel_timeout이 30초 간격으로만 적용된다. 15초 제한이 15~16초 안에 지켜지게 한다. 값 1은 근거 기록 없음 |
| max_request_body_size | 1,000,000 | 기존 상한(근거 기록 없음) |
| backlog | 128 | 기존 `request_queue_size`(부하 측정 N=50에서 5는 연결 거부) |

## 왜 (따른 표준과 근거)
PEP 3333(WSGI)은 앱과 서버의 표준 인터페이스이고, waitress는 순수 Python의 프로덕션 WSGI 서버로 slowloris(요청을 다 받은 뒤에야 작업 스레드를 쓴다)·연결 제한·본문 제한을 갖는다. prefork 서버(gunicorn)가 아닌 이유: 앱이 프로세스 안 상태(SSE 허브, 세션 락, 카운터)를 공유하는 단일 프로세스·다중 스레드 설계다. 병목은 모델 호출 대기(I/O)와 DB라 스레드로 충분하다는 것은 ADR-0004의 부하 측정(가짜 모델 기준)에 있다. 실제 모델로 측정하지 않았다.

## 검토한 대안과 버리는 이유
gunicorn(prefork): 프로세스 안 상태를 공유하는 설계와 맞지 않는다. uvicorn/ASGI: 앱 전체가 동기 코드라 이득이 없다. 현행 유지: 점검 B01·B02.

## 결과
얻는 것: 직접 만든 서버·방어 코드 삭제, 표준 서버의 읽기·연결 제한. 바뀐 동작(보고 대상):
1. 접속 상한을 넘으면 503 JSON이 아니라 새 연결을 받지 않는다(커널 대기열). 자리가 나면 처리된다.
2. 본문 상한(1,000,000) 초과는 400 INVALID_RECORD가 아니라 waitress의 413(본문은 text/plain)이다. 계약 PUBLIC_API.md의 상태 코드 표에 413이 없다. 클라이언트가 413을 어떻게 다룰지는 확인하지 못했다.
3. 숫자가 아니거나 음수인 Content-Length는 여전히 400이지만 본문은 waitress의 text/plain이다.
4. 지원하지 않는 메서드는 404 JSON(이전에는 501 HTML 등).
5. 연결은 HTTP/1.1 keep-alive이다(이전에는 요청마다 닫음).
감수하는 것: waitress는 앱이 처리 중일 때 클라이언트 끊김을 모른다(SSE는 다음 쓰기에서 안다, 하트비트 주기 안).

## 되돌리는 조건
다중 프로세스 확장이 필요하면 상태 공유(SSE 허브)를 외부로 옮긴 뒤 prefork 서버를 검토한다.
