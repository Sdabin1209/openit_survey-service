# ADR-0034: 결과 목록의 순서와 커서는 쓸 때마다 매기는 단조 증가 번호를 따른다

## 상태
승인(헤드 지시 OPEN_GAPS U26). 이전의 (updated_at, session_id) 순서를 대체한다.

## 맥락
`GET /v1/results`는 `updated_at`(벽시계 `time.time`) 순으로 정렬하고 커서를 `updated_at|session_id`로 했다. 이 PC(WSL2)에서 벽시계는 120초에 2번, 최대 155.7ms 되감긴다(헤드 측정). 되감기면 나중에 쓴 세션이 앞에 나오고, 커서가 쪽 사이에서 행을 빠뜨리거나 되풀이할 수 있다. 흔들린 시험(`test_result_list_filters_pagination_and_cursor[postgres]`)의 원인으로도 유력하다(확정은 못 했다).

## 결정
세션 표에 `update_seq`(정수)를 더하고 INSERT·UPDATE(커밋, 로그 추가)마다 저장소가 새 번호를 매긴다. SQLite는 `(SELECT COALESCE(MAX(update_seq), 0) + 1 FROM sessions)`이고 쓰기가 한 번에 하나라 겹치지 않는다. PostgreSQL은 시퀀스 `sessions_update_seq`의 `nextval`이다. 목록은 `update_seq` 오름차순이고 커서는 마지막으로 본 번호(10진 정수 문자열, 형식이 아니면 400)다. 시각(`updated_at`)은 `updated_after` 거르기와 유휴 만료·보존 기간 판정에만 쓴다. 마이그레이션 0006이 열·시퀀스·색인을 만들고 옛 행에 옛 순서(updated_at, session_id)로 번호를 채운다(yoyo, ADR-0030).

## 왜
순서에 시각을 쓰는 한 시계가 되감기면 순서가 흔들린다. DB가 정하는 단조 증가 번호는 시계와 무관하다(헤드 제안: DB가 매기는 단조 증가 열). 시퀀스는 PostgreSQL이 동시 쓰기에서 번호 중복을 막는 표준 수단이다.

## 검토한 대안과 버리는 이유
시계를 `time.monotonic`으로: 프로세스를 넘어 비교할 수 없고(재시작·여러 복제본) 저장하는 값이 의미를 잃는다. 프로세스 안에서 `max(time.time(), 직전+ε)`로 보정: 재시작 직후와 여러 복제본에서는 여전히 되감길 수 있다. 시퀀스 대신 MAX+1을 PostgreSQL에서도: 동시 쓰기에서 같은 번호가 나온다.

## 번호 순서 = 커밋 순서 (같은 날 보강)
처음 구현은 번호가 쓰기(번호를 받은) 순서였다. PostgreSQL에서 두 연결이 번호 5, 6을 받고 6이 먼저 커밋하면, 6까지 읽은 커서는 나중에 커밋된 5를 영구히 건너뛴다(결과를 이어 받는 병원 쪽이 행을 잃는다). 시험으로 재현했다(`tests/test_results_commit_order_u26.py`, 수정 전 PostgreSQL에서 커밋 순서 B,A와 번호 A=3,B=4).
비교한 방법: (a) 번호를 받는 쓰기 트랜잭션을 트랜잭션 수준 advisory lock(`pg_advisory_xact_lock`)으로 직렬화해 번호 순서 = 커밋 순서로 만들기. (b) 읽는 쪽이 진행 중인 트랜잭션보다 작은 번호까지만 내보내기(`pg_snapshot_xmin` 등으로 안전한 상한을 구하고 그 아래만 읽기). (c) 읽는 쪽이 마지막 쪽을 겹쳐 다시 읽고 중복을 제거하기.
고른 것: (a). 근거: 쓰기 쪽 한 곳(`_number_lock`)만 바뀌고 읽는 쪽과 커서는 그대로다. 소비자가 안전 상한을 알 필요가 없다. 이 서비스는 연결이 저장소마다 하나이고(ADR-0003) 세션 쓰기 하나는 수 ms라 직렬화 비용이 작다(복제본 여럿일 때만 서로 기다린다, 측정 안 함). (b)는 번호가 아닌 트랜잭션 ID 이해가 읽는 쪽에 필요하고 오래 열린 트랜잭션 하나가 목록 전체를 멈춘다. (c)는 소비자가 중복 제거를 해야 하고 겹치는 구간의 크기를 정할 근거가 없다.
방식: 번호를 받는 모든 쓰기(`create`, `commit`, 로그 추가)가 BEGIN 직후 같은 키의 advisory lock을 얻는다(키 7264003, 이 영역 고정값). 잠금은 커밋 또는 롤백에 풀린다. 다음 쓰기는 앞 쓰기가 커밋한 뒤에야 `nextval`을 받으므로 번호 순서 = 커밋 순서다. 잠금을 기다리는 시간은 연결의 문장 timeout(기본 2초)에 걸린다. 잠금을 쥔 쓰기가 느리면 기다리던 쓰기가 오류가 되고 턴은 실패로 처리된다(NOT_COMMITTED).
SQLite: 쓰기 트랜잭션이 `BEGIN IMMEDIATE`로 DB 쓰기 잠금을 커밋까지 쥐므로 한 번에 하나이고 번호 순서 = 커밋 순서다(같은 파일에 연결 둘로 시험).

## 결과
얻는 것: 시계와 무관한 순서, 커서가 행을 빠뜨리거나 되풀이하지 않는다(쪽 읽는 사이에 갱신된 세션은 뒤로 옮겨 다시 나올 수 있다: 마지막 쓴 순서이므로 의도). 감수하는 것: (1) PostgreSQL 세션 쓰기가 복제본 사이에서 직렬화된다. 롤백된 쓰기는 번호가 비어도 순서에는 영향이 없다. (2) 커서 형식이 바뀌었다(불투명 문자열이라 소비자 영향은 없다고 보지만 확인하지 못했다). (3) PostgreSQL 시퀀스는 롤백해도 번호가 비어 있을 수 있다(순서에는 영향 없음).

## 되돌리는 조건
쓰기 처리량이 직렬화에 막히면(복제본 여럿, 측정 필요) 방법 (b)로 바꾼다.
