# ADR-0011: DB 접속·문장 timeout, 재접속 유예, 우아한 종료

## 상태
/readyz 부분은 [ADR-0027](ADR-0027.md)이 대체했다(응답 전체 마감 하나). 승인(FAULT_POLICY 원칙 4·5), 값은 측정으로 조정

## 맥락
DB가 중지되거나 멈추면 턴이 접속 시도를 연달아 끝까지 기다려 마감을 넘겼다(측정: 중지 3.0초, pause 10.0초).

## 결정
`SURVEY_DB_CONNECT_TIMEOUT_SECONDS` 2, `SURVEY_DB_STATEMENT_TIMEOUT_SECONDS` 2(서버 `statement_timeout`과 상한+1초 뒤 클라이언트 소켓 강제 종료), `SURVEY_DB_RECONNECT_BACKOFF_SECONDS` 1(접속 실패 직후 바로 실패). /readyz는 주 연결 대신 별도 짧은 연결로 세 저장소를 동시에 확인하고 `SURVEY_READYZ_DB_TIMEOUT_SECONDS`(기본값은 `survey_service/settings.py`)를 세 확인 전체의 총 마감으로 건다(여유를 더하지 않는다. FAULT_POLICY 5가 2초 안 응답을 요구한다). SIGTERM은 draining 표시 후 처리 중 요청을 끝낸다.

## 왜 (따른 표준과 근거)
표준: 모든 외부 호출에 timeout, 빠른 실패(circuit-breaker식 짧은 유예), 헬스 체크는 요청 경로와 분리, graceful shutdown. 근거(측정, 이 PC): 유예 적용 뒤 중지 2.0초, pause 5.0초(boundary.md §5). libpq의 connect_timeout은 2초 미만이 의미 없다. **측정하지 않은 것**: compose 네트워크에서 중지 시 접속 거부인지 도달 불가인지.

근거(측정, 이 PC, 2026-10-28): 세 확인이 모두 멈출 때 /readyz 총 시간 5회 [2.001, 2.001, 2.002, 2.001, 2.002]초, 최악 2.002초(`tests/test_readyz_db_outage.py::test_readyz_deadline_measured_worst_case`가 출력). 이전 구현(마감+1초)은 전체 E2E에서 3.1초(1회). 마감 경계 시험: 마감보다 0.3초 일찍 끝난 확인은 정상, 0.3초 늦게 끝난 확인은 실패로 센다. 측정은 이 PC 한 곳이다.

## 검토한 대안과 버리는 이유
timeout을 줄이기만: 접속 시도가 단계마다 반복되는 구조 문제를 고치지 못한다. 연결 풀의 상태 검사: 풀이 없는 구조(ADR-0003)에서는 과하다.

## 결과
얻는 것: DB 장애 때 환자 경로의 상한. 감수하는 것: DB가 돌아와도 복구가 최대 1초 늦을 수 있다.

## 되돌리는 조건
연결 풀 도입 시 풀의 timeout 설정으로 대체한다.
