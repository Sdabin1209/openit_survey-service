# ADR-0018: HTTP 계층 방어: 소켓 읽기 제한, 접속·SSE 상한, 웹 푸시 SSRF 차단

## 상태
승인(감사 A9·B4·B6 대응, 2026-10-28)

## 맥락
표준 라이브러리 서버(ADR-0004)는 느린 클라이언트와 접속 폭주에 기본 방어가 없고, 직원이 등록한 푸시 URL로 서버가 요청을 보낸다.

## 결정
`SURVEY_SOCKET_TIMEOUT_SECONDS` 15(읽기 제한), `SURVEY_MAX_CONNECTIONS` 256(초과 시 503), `SURVEY_MAX_SSE_CONNECTIONS` 50, 비정상 Content-Length와 짝 없는 서로게이트 문자는 400, 401/403/429는 경고 로그와 `/readyz`의 `api` 카운터, 요청 ID(`X-Request-Id`)를 로그에 붙인다. 웹 푸시 endpoint는 등록 때 https·포트 443·공개 호스트 이름을 확인하고, 보낼 때 해석한 주소가 모두 공개(전역) 주소일 때만 보내며 리다이렉트를 따르지 않는다.

## 왜 (따른 표준과 근거)
표준: 모든 소켓 읽기에 timeout, 동시 접속 상한, SSRF 방어(사설·루프백·링크 로컬·메타데이터 주소 차단, 리다이렉트 미추적). 근거 출처: 감사 survey-service A9·B4·B6·E1. **측정하지 않은 값**: 15초, 256, 50은 근거 기록 없음(표준은 gateway 뒤 timeout 정렬; 부하 측정은 마감 8초 시절이고 이 상한 적용 뒤 재측정 안 함). 한계: DNS 재바인딩(해석과 연결 사이의 응답 변경)은 막지 못한다.

## 검토한 대안과 버리는 이유
gateway에만 맡기기: 이 서비스가 직접 열려 있는 구성(스모크, 개발)에서 방어가 없다. 허용 목록만(알려진 푸시 서비스 호스트): 운영 설정 값이라 구조만 두지 않았다.

## 결과
얻는 것: 스레드 고갈·SSRF 완화. 감수하는 것: 정상 느린 클라이언트도 15초에 끊긴다, 접속 상한이 정상 부하 대비 충분한지 측정 안 함.

## 되돌리는 조건
실제 부하·gateway 설정이 측정되면 값을 재정한다. DNS 재바인딩까지 막으려면 해석한 주소로 연결을 고정한다.
