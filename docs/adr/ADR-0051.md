# ADR-0051: 직원 경로의 요청 전체 마감 9.0초

## 상태
승인(헤드 지시 U427 후속, 2026-10-31). 와이어 형식은 바뀌지 않는다. 마감을 넘기면 기존 오류 코드 UNAVAILABLE(503)이다.

## 맥락
직원 경로의 노출 선언은 dial 1000 + response_header 9500(= 10.5초)이다(시간 사슬 D119·D120, ADR-0049). 알림 목록·직원 세션 보기·푸시 구독 등록은 한 요청에서 DB 문장을 여러 번 실행한다. 문장 하나의 상한(접속 2.0 + 문장 2.0)은 있었으나 요청 전체의 상한이 없어, 문장이 많으면 최악 시간이 9.5초를 넘을 수 있었다(코드로 확인한 것이 아니라 상한이 없다는 사실에서 나온 판단).

## 결정
- 설정 `request_deadline_seconds`(환경 변수 `SURVEY_REQUEST_DEADLINE_SECONDS`, 기본 9.0)를 둔다. `Orchestrator.request_until()`이 주입 시계로 마감 시각을 정하고, `Orchestrator.bounded(fn, until)`이 DB 문장 하나를 마감까지만 기다린다. 남은 시간이 그 문장의 상한이고, 넘기면 StoreError를 내 기존 처리가 503 UNAVAILABLE로 바꾼다.
- 적용: 알림 목록, 직원 세션 보기(상태 읽기·접근 기록·타임라인·알림·대상·릴리스), 푸시 구독 등록. 개입(intervention)은 턴 마감 9.0이 이미 있어 그대로다.

## 왜
9.0은 턴 마감(ADR-0049)과 같은 값이다. 서버 시한 9.0 < gateway 10.5 사슬을 한 값으로 지킨다. 측정하지 않았다. 표준 라이브러리 스레드와 주입 시계(ADR-0050)를 썼다.

## 검토한 대안과 버리는 이유
- 문장마다 같은 상한: 문장 수에 비례해 늘어나 사슬을 지키지 못한다.
- DB 드라이버의 문장 시한을 남은 시간으로 바꾸기: 저장소 컴포넌트가 요청 마감을 알아야 해 구조 규칙 3·4(컴포넌트는 자기 입출력만)에 어긋난다.

## 결과
요청 응답 머리글이 9.0초 안에 나온다. 넘긴 문장의 스레드는 데몬으로 버려지고 문장 자체의 statement_timeout이 끝낸다.

## 되돌리는 조건
시간 사슬이 바뀌거나 저장소가 요청 단위 마감을 직접 받는 구조로 바뀔 때. 시험: tests/test_request_deadline.py, tests/test_exposure.py.
