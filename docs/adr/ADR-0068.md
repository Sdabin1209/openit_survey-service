# ADR-0068: 계약 5.0.0 반영: ID 타입 위임, 검증기 한 곳, 4.x 저장 데이터는 드러낸다

## 상태
승인(헤드 지시 2026-11-08, 계약 v5.0.0 CHANGELOG). ADR-0066(세션 ID 발급)과 ADR-0067을 바꾸지 않는다.

## 맥락
계약 5.0.0이 ID 타입을 통일하고(SessionId·Id·QuestionId·HumanUserId), `envelope_id` 정본 함수와 JSON 공통 규칙(NaN·Infinity 거부, 깊이·크기), 사람 입구 입력 상한(커서·Last-Event-ID 18자리)을 정했다. 영역에는 같은 뜻의 사본이 있었다: `schemas/`의 패턴 56곳, 자체 `envelope_id`, 손으로 쓴 쿼리 검사, 직접 만든 jsonschema 검증기.

## 결정
- 영역 `schemas/`의 ID 패턴 사본은 지우고 `x-contract`로 계약 정의(`_common#/$defs/SessionId`·`Id`·`HumanUserId`, subject_ref, DeviceAllowlist의 device_id)에 위임한다. `survey_service/types/validation.py`가 그 키를 따라가 계약 검증기로 본다.
- 검증기는 `types.draft_validator` 한 곳에서 만든다: 계약 `ContractValidator`(비유한 수 거부)와 계약 registry(외부 `$ref`를 오프라인으로 푼다). `jsonschema.Draft202012Validator`를 직접 만들지 않는다. 오류에는 위반한 값을 싣지 않는다(위치와 키워드만, INTERFACES I7).
- `envelope_id`는 `boundary_contracts.envelope_id`를 쓴다(자체 구현 삭제).
- 알림·결과 쿼리는 계약 `HttpQueries.Alerts`·`Results` 전체로, Last-Event-ID는 `HttpWire.EventId`로 검증한 뒤에만 `int()`를 한다.
- outbox에 주 버전이 다른(4.x) 봉투가 보낼 차례이거나 DEAD로 남아 있으면 `/readyz`가 `stored_pipeline_major_mismatch`로 준비 안 됨을 낸다.

## 왜
- 같은 뜻의 타입은 한 번만 정의한다(D117). 사본은 계약이 바뀔 때 어긋난다(끝 줄바꿈 패턴 누락으로 Trace가 거부된 일, 결함 #17·#23).
- 계약 검증기를 거치지 않으면 NaN·무한대가 `number` 칸을 통과한다(계약 5.0.0 CHANGELOG).
- 4.x 저장 데이터는 이전하지 않는다는 헤드 결정(새 환경 전제)이므로 섞이지 않고 드러나야 한다.

## 검토한 대안과 버리는 이유
- 쿼리 손 검사를 남기기: 같은 규칙의 사본이라 계약과 어긋난다.
- 4.x 봉투를 5.0으로 변환해 보내기: 이전 경로가 없다는 결정과 충돌하고 세션 ID가 `_`로 시작하는 기록은 변환할 수 없다.

## 결과
얻는 것: 사본 제거, 입구 500 경로 차단, 4.x 혼용 방지. 감수하는 것: 계약 registry 생성이 느려 모듈당 한 번만 만든다(`lru_cache`). `ApiRequest.json`의 경로 정규식과 계약에 대응이 없는 ID(signal_id 등)는 남았다. 문진 스키마(`schema/`) 자체의 위임은 계약 안정 URI가 있는 태그 뒤 별도 단계다.

## 되돌리는 조건
계약이 ID 정의를 다시 나누거나 registry 제공 방식을 바꿀 때.
