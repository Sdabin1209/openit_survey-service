# ADR-0020: 연속 되묻기 상한 N=3, 4번째에 직원 호출 (G12)

Supersedes: [ADR-0014](ADR-0014.md)

## 상태
반복 정의는 ADR-0032가 넓혔다(REDIRECT와 추출·검증 실패 턴도 센다). 값 3과 정지 방식은 그대로다.
승인(헤드 결정). 값은 측정하지 않았다.

## 맥락
A(추출)가 REASK·CONFIRM만 내면 환자가 문진을 끝내지 못하고 직원도 모른다(감사 I1, G12). ADR-0014는 잠정값 3으로 기본을 켰으나 값과 정지 이름 재사용은 미정이었다.

## 결정
`SURVEY_MAX_CONSECUTIVE_REASK` 기본 **3**(0이면 끔). 반복의 정의는 코드(`graph.py` `_reask_escalation`)와 같다: 대화 로그에서 **REASK 또는 CONFIRM이 연속으로 나온 COMMITTED 턴 수**(둘을 합산, 문항과 무관). 그 외 action이거나 재개·시작 같은 턴이 나오면 센 값이 0으로 돌아간다. 이미 3턴 연속이고 4번째에도 REASK·CONFIRM이 나오면 되묻는 대신 기존 직원 호출 경로로 간다: 세션 `PAUSED_RISK`, `CALL_STAFF` 알림, 고정 문장 `CALL_STAFF`. 문항 세트의 `ask_limit`·`confirm_limit`·`unrecognized_streak_limit`가 있으면 그 최솟값이 이긴다(근사는 ADR-0014 그대로).

## 왜
- 표준 대화 설계의 관행: 같은 요청을 2~3번 되물어도 안 되면 사람에게 넘긴다(대화형 시스템의 fallback/escalation 관행).
- 이 워크스페이스의 FAULT_POLICY가 재시도를 3회로 두는 관행과 맞춘다.
- 새 정지 경로를 만들지 않고 이미 시험된 직원 호출 경로를 재사용한다(새 문구 없음, 알림·SSE·푸시 그대로).
- **측정하지 않았다**: 학습 데이터는 단일 턴이라 연속 REASK의 실제 빈도를 잴 수 없다. 3은 관행에서 온 값이다.

## 검토한 대안과 버리는 이유
- 끄기(이전 기본): 무한 되묻기 가능. 버린다.
- 2: 정상적인 한 번의 REASK 뒤 CONFIRM 같은 흐름까지 직원을 부를 수 있다. 측정 없이 줄일 근거가 없다.
- 문항별 따로 세기: 코드·대화 로그의 정의(합산 연속)와 다르고 현재 로그로는 같은 문항 판정이 추가 설계를 요한다. 헤드가 코드의 정의를 택했다.
- 별도 정지 이름: 이웃 계약(PUBLIC_API의 상태 이름) 변경이 필요해 지금은 하지 않는다.

## 결과
얻는 것: 되묻기 무한 반복이 막히고 직원이 안다. 감수하는 것: (1) 정상 대화가 길면 직원 호출이 늘 수 있다. (2) **정지 이름 `PAUSED_RISK` 재사용의 의미 불일치**: 위험이 아니라 반복 실패인데 같은 정지로 보인다. 공개 계약 확인 결과 `GET /v1/sessions/{id}/state`는 `state`(ACTIVE/PAUSED_RISK/ENDED)만 주고 사유가 없다. 턴 응답은 위험 정지와 같은 모양의 `turn_failure_signal`(`COMMITTED`, `staff_alert=DELIVERED`)을 낸다. 구분 수단은 고정 문장(`response_text`)뿐이다. 키오스크가 둘을 다르게 보이려면 계약에 사유 필드가 필요하다(헤드 판단, 변경 요청 대상). kiosk-frontend 코드는 읽지 않았다(워크스페이스 규칙).

## 되돌리는 조건
`SURVEY_MAX_CONSECUTIVE_REASK=0`으로 끈다. H1 같은 다중 턴 데이터를 얻으면 값을 다시 정한다. 계약에 정지 사유가 생기면 이름 재사용 감수를 거둔다.
