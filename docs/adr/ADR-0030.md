# ADR-0030: 스키마는 yoyo-migrations의 번호 붙은 마이그레이션으로 만들고 바꾼다

## 상태
승인(헤드 결정 D111, 2026-10-29). 시작 때 직접 만든 스키마 생성·이행(표준 점검 A05)을 대체한다. ADR-0002의 "멱등 생성"을 이 방식으로 바꾼다.

## 맥락
이전에는 저장소를 열 때마다 `CREATE TABLE IF NOT EXISTS`를 실행하고, 나중에 더한 열은 `_NEW_COLUMNS`/`PRAGMA table_info` 검사로 `ALTER`했으며, PostgreSQL은 advisory lock으로 동시 시작을 막았다. 어떤 버전이 어디까지 적용됐는지 기록이 없고 SQLite와 PostgreSQL 방언도 `pg_ddl`이 문자열 치환으로 맞췄다. 버전 있는 마이그레이션 도구가 표준이다.

## 결정
`yoyo-migrations==9.0.0`. 데이터베이스 종류마다 디렉터리 하나(`survey_service/migrations/sqlite/`, `.../postgresql/`)이고 번호 순서가 전부다: 0001 outbox, 0002 세션·턴, 0003 알림 등, 0004·0005는 yoyo 도입 전 코드가 나중에 더한 열을 옛 파일에 채우는 다리다(새 데이터베이스에서는 아무 일도 하지 않는다). 저장소는 열 때 `migrate(kind, target)`을 부른다. 적용 기록(`_yoyo_migration`, `_yoyo_log`)과 동시 실행 잠금(`yoyo_lock`)은 yoyo가 맡는다. 지운 것: `_SCHEMA` 문자열들, `_NEW_COLUMNS`, `pg_ddl`, `PgConn.script`와 advisory lock 키.

## 왜 (따른 표준과 근거)
버전 있는 마이그레이션 도구(Alembic, Flyway, yoyo 류)가 표준이다. yoyo를 고른 이유: ORM이 없고(ADR-0003) SQL 파일을 그대로 적용하면 되는 도구가 맞고, SQLite와 PostgreSQL(psycopg 3)을 모두 지원하며, 잠금을 직접 구현하지 않아도 된다. 대안 Alembic은 SQLAlchemy를 끌어오고 이 영역은 ORM을 쓰지 않는다(ADR-0003). 한 데이터베이스에 목록을 여럿 두지 않은 이유: 세트별 적용 기록 표를 쓰려 했으나 yoyo의 내부 표(`_yoyo_log`)가 데이터베이스마다 하나라 두 번째 목록에서 "already exists"로 실패했다(측정). 결과로 SQLite 알림 파일에도 세션·outbox 표가 함께 생긴다(쓰지 않는 표).

## 이미 있는 스키마
0001~0003은 `IF NOT EXISTS`다: yoyo 도입 전 코드가 만든 데이터베이스에서는 표를 건드리지 않고 적용 기록만 남는다. 더 옛 데이터베이스(열이 빠진 것)는 0004·0005가 채운다(SQLite는 `ADD COLUMN IF NOT EXISTS`가 없어 파이썬 마이그레이션이 `PRAGMA table_info`로 확인한다). 시험: `tests/test_migrations.py`(새 파일, 기존 스키마와 데이터 유지, 열이 빠진 옛 파일, 두 번 적용, SQLite·PostgreSQL이 같은 표와 열을 가짐).

## 검토한 대안과 버리는 이유
현행 유지: 점검 A05(O). Alembic: 위. 앱이 시작할 때 적용하지 않고 별도 잡으로만: 서비스 한 대·단일 프로세스 배포에서 순서가 늘 보장되지 않고, yoyo 잠금이 동시 시작을 막는다. 별도 잡 분리는 deploy의 결정 사항으로 남긴다.

## 결과
얻는 것: 스키마 버전 기록, 표준 도구의 잠금, 앞으로의 변경은 새 번호 파일 하나. 감수하는 것: 시작 때 마이그레이션 접속이 한 번 더 일어난다(저장소마다 호출, 두 번째부터는 적용할 것이 없어 확인만 한다). yoyo의 PostgreSQL 접속에는 이 영역의 문장 timeout 설정이 적용되지 않는다. 롤백 마이그레이션은 쓰지 않는다(앞으로만).

## 되돌리는 조건
yoyo가 psycopg 3 지원을 잃거나 이 영역이 SQLAlchemy를 도입하면 Alembic으로 옮긴다.
