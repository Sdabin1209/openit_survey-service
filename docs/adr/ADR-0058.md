# ADR-0058: 직원 알림 재시도 큐 (L14)

## 상태
승인(헤드 지시 2026-11-03, 작업 L14).

## 맥락
위험·직원 호출 알림은 알림 DB에 저장한 뒤 전달한다. 알림 DB가 죽어 있으면 `create`가 `StoreError`로 실패해 알림이 사라졌다(세션은 위험 정지로 기록되지만 직원에게 알림 기록이 남지 않는다).

## 결정
- 알림 DB에 쓰지 못하면(`StoreError`) 알림(세션, 턴, 종류, 규칙, 정지 사유)을 **세션 DB의 `alert_queue` 표**(마이그레이션 0008)에 한 줄 남기고 원래 오류는 그대로 올린다(턴 처리의 기존 실패 경로는 바뀌지 않는다).
- `(세션, 턴, 종류)`가 유일하다: 같은 알림을 두 번 넣어도 한 줄이다.
- 서비스의 `alert-queue` 스레드가 `settings.export_interval_seconds`마다 `AlertService.drain_queue`를 부른다. 큐의 알림을 `raise_alert`의 같은 경로(멱등 `find_by_turn`)로 다시 저장·전달하고, 저장되면 행을 지운다(전달 경로가 없어 `DeliveryFailed`여도 알림은 저장된 것이라 지운다: 전달 실패 표시가 직원 콘솔에 남는다). 알림 DB가 아직 안 되면 `next_attempt_at`을 지수 백오프(5초 시작, 최대 60초)로 미룬다.
- `/readyz`의 `staff_alerts.queue`에 `pending`, `oldest_age_s`를 낸다.

## 왜
- 세션 DB에 둔 이유: 알림 DB가 죽은 순간 쓸 수 있는 저장소가 필요하고, Trace outbox와 같은 DB·같은 구조(D16, 영속 큐 + 주기 재시도)라 새 인프라가 없다.
- 멱등 키가 (세션, 턴, 종류)인 이유: 알림 생성의 기존 멱등 키와 같다(`find_by_turn`).
- 주기와 백오프 값은 Trace 내보내기의 기존 값(5초 시작, 60초 상한, 같은 설정)을 따랐다. 알림 큐에 대해 측정하지 않았다.

## 검토한 대안과 버리는 이유
- 알림 DB와 같은 DB에 두기: 알림 DB 장애에서 함께 죽는다.
- 턴 안에서 즉시 재시도: 턴 마감(FAULT_POLICY)을 갉아먹고 위험 정지 응답이 늦어진다.

## 결과
얻는 것: 알림 DB 장애 중 생긴 알림이 복구 뒤 직원에게 닿는다. 감수하는 것: 세션 DB도 동시에 죽으면 여전히 잃는다(원래 오류가 올라간다). 복구 뒤에 도착하므로 알림 시각은 늦다.

## 되돌리는 조건
알림 저장소를 세션 DB와 합칠 때.
