# ADR-0052: 시간 상한은 목표가 아니라 실패 판정 기준: extract 21 / respond 26 / 턴 마감 50 (ADR-0049를 대체)

## 상태
승인(사용자 결정 D125, 2026-11-02). Supersedes: ADR-0049의 값(extract 3.0, respond 5.0, 턴 9.0). ADR-0026의 재시도 규칙과 ADR-0051의 구조는 유효.

## 맥락
"환자 턴 2초"는 목표(SLO)인데 그 근처 값을 실패 상한으로 썼다. 첫 턴 extract가 JIT로 3.0초를 넘어 턴이 실패했다(H4 실측 2026-11-02).

## 결정
`SURVEY_INFERENCE_EXTRACT_TIMEOUT_SECONDS` 21.0, `SURVEY_INFERENCE_RESPOND_TIMEOUT_SECONDS` 26.0, `SURVEY_TURN_DEADLINE_SECONDS` 50.0. 노출 선언의 응답 헤더 상한은 9500 -> 55000ms(gateway 56초). 재시도는 남은 턴 예산이 호출 상한 이상일 때만 한다(그대로).

## 왜
계약 CONVENTIONS "시간 상한 사슬"(D125)의 표를 따른다. 표준: HTTP 프록시·LB 기본 읽기 상한 60초(nginx, ALB). 클라이언트 상한은 model-runtime 서버 상한(20/25)보다 1초 길어야 서버가 먼저 503을 내 원인이 분명하다. 서버 상한 합 45 + 여유 5 = 턴 마감 50 < gateway 56 < 키오스크 60. 값은 측정이 아니라 표준·여유에서 나왔고 측정하지 않았다.

## 검토한 대안
- 3.0/5.0/9.0 유지: 정상 지연(JIT)에도 턴이 실패해 버린다.
- 클라이언트 상한을 서버와 같게(20/25): 어느 쪽이 먼저 끊는지 경쟁한다.

## 결과
정상 지연에 턴이 실패하지 않는다. 진짜 장애의 감지는 최대 50초 늦어진다. 2초 목표는 지표로 본다.

## 되돌리는 조건
GPU 실측으로 최악값이 확인되고 사용자가 상한을 다시 정할 때.
