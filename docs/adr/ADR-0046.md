# ADR-0046: /readyz가 되묻기 실효 한도를 낸다

## 상태
승인(헤드 지시 wo-320 추가).

## 맥락
되묻기 연속 상한의 실효 값은 `min(SURVEY_MAX_CONSECUTIVE_REASK(켜져 있을 때), 문항 세트 ask_limit·confirm_limit·unrecognized_streak_limit 중 1 이상 정수)`다(ADR-0014, ADR-0020, `graph.py`). deploy E2E가 이 규칙을 따로 계산하고 있었다(헤드가 알려 준 사실, deploy 코드는 읽지 못했다). 이웃이 이 영역의 내부 규칙을 알면 구조 규칙 4(자기 입출력 스키마와 업무밖에 모른다)에 어긋나고, 규칙이 바뀔 때 어긋난다.

## 결정
규칙을 `graph.effective_reask_cap(max_consecutive, session_settings)` 한 함수로 두고 그래프(`_reask_cap`)와 `/readyz`가 같은 함수를 쓴다. `/readyz.reask_limit`는 `{active, max_consecutive, effective}`다. `effective`는 활성 릴리스의 문항 세트까지 반영한 값(0=끔), 활성 릴리스가 없으면 null이다. `active`는 effective가 있으면 effective>0, 없으면 서비스 설정>0이다.

## 왜
- 값을 아는 영역이 한 곳에서 계산해 내보내고 이웃은 읽기만 한다(루트 CLAUDE.md "한 사실은 그것을 아는 영역이 한 곳에서만").
- 그래프와 `/readyz`가 같은 함수를 호출하므로 실제 적용 값과 보고 값이 어긋나지 않는다(시험이 규칙과 보고 값을 모두 본다).

## 검토한 대안과 버리는 이유
- 이웃이 규칙을 흉내 낸다: 구조 규칙 4 위반이다.
- 활성 릴리스 없을 때 서비스 설정값을 effective로 낸다: 문항 세트가 더 작은 값을 정할 수 있으므로 거짓 값이 된다. null로 낸다.

## 결과
얻는 것: 이웃이 내부 규칙을 몰라도 된다. 감수하는 것: `/readyz` 필드가 늘었다. 계약 `SurveyReadyz`는 `reask_limit`를 속성으로 정의하지 않고 추가 속성을 막지 않으므로(이 세션에서 스키마를 읽어 확인) 계약을 어기지 않는다. 다만 이 필드의 모양이 계약에 적히지 않았다는 점은 헤드가 정할 일이다.

## 되돌리는 조건
계약 `SurveyReadyz`가 `reask_limit` 모양을 다르게 정하면 계약에 맞춘다.
