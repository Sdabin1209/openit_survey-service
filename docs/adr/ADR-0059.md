# ADR-0059: 결과 도착 웹 푸시 - 구독 주제(topics)와 RESULT_READY (U92)

## 상태
승인(헤드 지시 2026-11-03, 계약 3.4.0 PUBLIC_API B절).

## 맥락
의사(clinician)가 화면을 닫아도 결과 도착을 알아야 한다. 웹 푸시 구독은 직원 알림용이라 역할 구분이 없었다.

## 결정
- 푸시 구독 본문에 선택 `topics`(`alerts`, `results`; 없으면 `["alerts"]`)를 받아 구독 JSON에 저장한다(스키마 변경 없음, 옛 구독은 주제가 없으면 alerts). `alerts`는 staff 역할, `results`는 result-reader 토큰(게이트웨이의 clinician 역할)만 등록할 수 있고 역할이 맞지 않으면 403 `PERMISSION_DENIED`다. 한 요청에 둘을 섞으면 어느 역할도 둘 다 갖지 못하므로 403이다.
- 푸시 경로 3개(`push-config`, 구독 등록, 해지)는 staff와 result-reader 둘 다 호출할 수 있다. `deploy-exposure.json`에 clinician 계정용 선언을 더했다(상류 토큰 `survey-result-reader`).
- 세션이 ENDED_*로 확정되면 기존 `result_ready` SSE에 더해 `results` 구독자에게 `StaffPushPayload{session_id, kind:"RESULT_READY"}`를 같은 발송기로 보낸다(subject_ref·값 없음). 직원 알림 푸시는 `alerts` 구독자에게만 간다. 주제 표시는 푸시 서비스에는 보내지 않는다.
- 발송 실패(대상이 있는데 접수 0)는 L14 재시도 큐(ADR-0058)에 `RESULT_READY` 행으로 넣고, 같은 지수 백오프로 다시 보낸다. 상한 10회를 넘으면 포기한다.

## 보강 (S7, 계약 3.4.0 CONVENTIONS 6절)
게이트웨이가 `X-Openit-Roles`(역할 쉼표 목록, 고정 목록)를 붙이므로, push 경로(`push-config`, 구독 등록, 해지)는 게이트웨이 토큰(staff 또는 result-reader)으로 들어온 요청의 이 헤더를 읽는다: `alerts`는 역할 `staff`, `results`는 역할 `clinician`이 있으면 허용한다. 한 사람이 둘 다 가지면 게이트웨이가 토큰을 하나만 붙여도 두 주제를 구독할 수 있다. 헤더가 없으면(직접 호출, 옛 경로) 위의 토큰 종류 판단 그대로다(호환). 게이트웨이 토큰이 아닌 요청(키오스크 등)은 경로의 역할 표 때문에 이 경로에 올 수 없어 위조 헤더는 읽히지 않는다. 고정 목록 밖의 역할 이름은 무시한다.

## 왜
- 역할을 토큰 역할에 묶었다: 호출자가 주장하는 값이 아니라 서버가 토큰에 묶은 역할만 믿는다(계약 CONVENTIONS 9절).
- 턴을 막지 않으려고 푸시는 별도 스레드에서 보낸다(접수 대기 최대 push_timeout).
- 재시도 상한 10회는 측정하지 않은 값이다(5초 시작, 최대 60초 간격이면 약 8분). 결과는 목록 API로 언제든 다시 맞출 수 있는 파생 정보라 무한 재시도하지 않는다.

## 검토한 대안과 버리는 이유
- 구독 표를 주제별로 나눈다: 같은 endpoint가 두 주제를 가질 수 있고 마이그레이션이 필요하다. JSON 필드로 충분하다.
- 실패를 재시도하지 않는다: 계약이 직원 알림과 같은 재시도 규칙을 요구한다.

## 결과
얻는 것: 화면을 닫은 의사도 도착을 안다. 감수하는 것: 서비스를 재시작하면 스레드에서 보내던 푸시는 재시도 큐에 들어가기 전에 사라질 수 있다(결과 목록으로 맞춘다).

## 되돌리는 조건
계약이 결과 푸시를 없앨 때.
