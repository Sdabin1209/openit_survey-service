# ADR-0007: 같은 turn_id는 멱등이고 세션 락으로 순서를 지킨다

## 상태
승인(D55, PUBLIC_API.md), 처리 중 409는 FAULT_POLICY 원칙 2

## 맥락
키오스크는 시간 초과 때 같은 turn_id로 재전송한다. 같은 턴이 두 번 처리되면 값이 이중 저장된다.

## 결정
(세션, turn_id)가 기본키이고 입력 해시를 비교한다. 확정된 턴은 저장된 결과를 그대로 돌려주고, 처리 중에 같은 turn_id가 오면 `409 CONFLICT`에 `details.reason=TURN_IN_PROGRESS`와 `Retry-After`를 낸다. 같은 세션의 다른 턴은 세션 락으로 순서대로 처리한다. 확정되지 못한 턴(NOT_COMMITTED)은 결과를 고정하지 않고 재전송이 새로 처리된다(CR-D25).

## 왜 (따른 표준과 근거)
표준: 멱등 키(Idempotency-Key) 패턴과 처리 중 충돌에 409. 근거 출처: boundary-contracts PUBLIC_API.md, HTTP.md의 409 사유 규약(CR-015 처리됨), FAULT_POLICY.md 원칙 1·2, deploy CR-D25. 동시 두 요청 시험(`tests/test_turn_idempotency_deadline.py`).

## 검토한 대안과 버리는 이유
락에서 기다렸다가 저장된 결과를 주기(이전 동작): 값은 이중 저장되지 않았지만 요청이 대기열에 쌓이고 클라이언트의 시간 초과와 겹친다. 실패 응답도 고정하기: 모델이 복구돼도 같은 turn_id가 영영 실패한다(CR-D25).

## 결과
얻는 것: 재전송 안전, 겹침 시 빠른 409. 감수하는 것: 세션 락과 in-flight 집합이 프로세스 안에만 있다(프로세스를 늘리면 PostgreSQL 행 잠금과 revision 검사에 의존), 마감 직전에 시작된 확정이 뒤늦게 반영되는 경합(boundary.md 한계).

## 되돌리는 조건
프로세스 복제를 도입할 때(세션 락을 DB 수준으로 옮길지 검토).
