# ADR-0035: 서버가 fields로 보증하는 값 규칙은 서비스가 다시 검사하지 않는다 (U24, R7)

## 상태
승인(헤드 지시 U24). ADR-0017의 3)번(서비스 값 검증)을 칸 규격이 있는 칸에서 대체한다. ADR-0028(의미 규칙은 서버가 보증)의 이어지는 결정이다.

## 맥락
model-runtime(main f99cf5a)은 ExtractRequest에 `fields`(QuestionFieldSpec)가 있으면 의미 규칙(`check_action_extraction`)과 값 규칙(`apply_value_rules`: 자료형·범위·선택지, 범위 밖은 데이터셋 정답 모양으로 바꾸고 바꿀 수 없는 위반은 503 OUTPUT_INVALID)을 보증한다. 서비스에는 같은 성격의 검사 4가지가 남아 있었다.

## 결정
서버 규칙으로 덮이는지 하나씩 대조했다(계약 `action_rules.py`를 읽음).
| 검사 | 서버 규칙으로 덮이는가 | 결정 |
|---|---|---|
| VALUE_INVALID(값 형식·크기: 숫자 100만 이하, 문자열 200자 이하, 빈 문자열) | 칸 규격이 있는 칸은 자료형 불일치·최소 미만·최대 초과를 서버가 본다. 규격이 없는 칸은 보지 않는다 | 규격이 있는 칸은 삭제, 없는 칸은 유지 |
| VALUE_TYPE_MISMATCH(선택지, 예/아니오, 단위, 이미 저장된 값과 종류) | 규격이 있는 칸은 자료형과 option 선택지를 서버가 본다(종류는 칸마다 고정). 없는 칸은 보지 않는다 | 규격이 있는 칸은 삭제, 없는 칸은 유지 |
| UNKNOWN_SLOT(저장하려는 칸이 문항 은행에 있는가) | **아니다.** 서버는 flow 문항만 안다(`UNKNOWN_ITEM`). 문항 안의 칸 이름은 보지 않고 `fields`에 없는 칸은 건너뛴다 | 유지 |
| OUT_OF_CURRENT_ITEM(현재 문항 밖 칸 저장) | **아니다.** 서버는 세션의 현재 문항 진행(같은 계열·next_item 구간)을 모른다 | 유지 |
칸 규격이 있는지는 칸마다 본다(`data_type`이 적힌 칸). 규격이 없는 문항 은행(2.x 호환)과 규격이 없는 칸에는 값 검사가 그대로 남고, 위반 때 같은 요청을 한 번 다시 보내는 것(D75)도 남은 검사에 그대로 적용된다. 삭제한 검사는 위반이 나올 수 없으므로 재호출도 함께 사라진다.

## 왜
R7: 한 컴포넌트가 보증한 값을 다른 컴포넌트가 다시 검사하지 않는다. 덮이지 않는 것은 아무도 보증하지 않으므로 서비스에 남긴다(지우면 틀린 칸이 저장될 수 있다: U07, TE-1). 시작 때 `fields`가 없는 문항 은행을 설정 오류로 거부하지 않은 이유: 문항 저작(question-authoring)이 새 칸 속성을 채우기 전의 은행으로도 서비스가 서야 하고, 그 은행의 값 검사를 서비스가 대신하면 안전하다.

## 검토한 대안과 버리는 이유
규격 없는 은행을 시작 때 거부: 배포 순서에 묶인다(저작 쪽이 먼저 바뀌어야 한다). 4가지를 모두 삭제: UNKNOWN_SLOT·OUT_OF_CURRENT_ITEM이 덮이지 않는다. 4가지를 모두 유지: R7 위반.

## 결과
얻는 것: 규격이 있는 칸에서 중복 검사 제거. 감수하는 것: (1) 서버가 `fields`를 적용하지 않는 구버전이면 규격이 있는 칸의 값 검사가 사라져 틀린 값이 저장될 수 있다. model-runtime v0.9.0(ade221c)은 `fields`를 알지 못하고, f99cf5a 이후 태그가 나와야 한다. 이 영역의 핀은 아직 v0.9.0이다. 서버와 이 변경의 순서를 지켜야 한다(서버 먼저). (2) 규격이 있는 칸이어도 `fields`에 없는 칸(문항 은행이 규격을 덮지 않은 칸)은 서버가 건너뛰므로 서비스가 값 검사를 한다.

## 되돌리는 조건
서버가 문항 은행의 칸 목록과 현재 문항을 알게 되면(예: 규칙 명세에 현재 문항을 입력으로 추가) UNKNOWN_SLOT·OUT_OF_CURRENT_ITEM도 서버로 옮기고 지운다.
