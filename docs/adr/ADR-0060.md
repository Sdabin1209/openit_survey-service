# ADR-0060: 데이터베이스는 이 영역의 컴포넌트다 - 엔진·버전·접속 대기·백업 잡, 요청 본문 상한, 잡 시간 상한

## 상태
승인(헤드 코드 단계 지시 2026-11-04, 계약 3.4.8: CONVENTIONS 13절, RUNTIME R10.1·R9.2·R3.10·R4.1, Exposure.max_body_bytes, JobsDeclaration.timeout_seconds).

## 맥락
데이터베이스는 영역 사이를 지나지 않는 이 영역의 컴포넌트다(Database per Service). 다른 영역의 DB 계정·접속은 없고, 백업은 영역이 자기 데이터를 꺼내 자기 영역 게이트웨이 출구로 platform 백업 저장소에 보낸다.

## 결정
- **엔진·버전**: 운영은 PostgreSQL 16(주 버전, `compose.dev.yaml`의 개발용도 같은 16), 개발·시험은 SQLite 파일. 세션·Trace outbox·알림·재시도 큐가 한 데이터베이스다(Trace outbox를 세션 commit과 같은 트랜잭션에 쓰려고, ADR-0023). 스키마는 yoyo 마이그레이션이 만든다(ADR-0030). 접속 문자열은 비밀 파일(`SURVEY_DATABASE_URL_FILE`)이고 `sslmode` 등 파라미터를 코드가 덮어쓰지 않는다.
- **접속 대기**: 접속 상한 `SURVEY_DB_CONNECT_TIMEOUT_SECONDS`(기본 2.0), 문장 상한 `SURVEY_DB_STATEMENT_TIMEOUT_SECONDS`(기본 2.0), `/readyz`의 DB 확인 총 상한 `SURVEY_READYZ_DB_TIMEOUT_SECONDS`(기본 2.0, 계약 FAULT_POLICY 5의 2초 안 503), 끊긴 연결은 요청 경로에서 스스로 다시 맺는다(재접속 유예 `SURVEY_DB_RECONNECT_BACKOFF_SECONDS` 기본 1.0). 값은 계약 SurveyServiceEnv의 기본값이고 측정하지 않았다(시작값). 접속·문장·확인이 이 상한에 닿으면 저장소 실패이고 응답은 503 UNAVAILABLE이다(R3.10, R3.19).
- **백업 잡** `python -m survey_service backup`(잡 선언 `backup`, 멱등): 일관된 한 시점의 덤프를 임시 폴더에 만들고(PostgreSQL은 한 REPEATABLE READ 읽기 전용 트랜잭션의 표별 `COPY ... TO STDOUT (FORMAT binary)`, SQLite는 온라인 백업 API), `restic backup`으로 `OPENIT_BACKUP_URL`(restic REST, https)에 올린다. 나가는 길은 `OPENIT_EGRESS_PROXY`(자기 영역 게이트웨이의 CONNECT 터널, 표준 `HTTPS_PROXY`로 restic에 준다). 비밀(백업 자격·저장소 암호·DB 접속 문자열)은 파일로 받는다. 출력은 마지막 줄 `BackupJobResult`, 종료 코드 0(ok)·75(백업 저장소·DB에 닿지 못함, 재시도 가능)·1(그 밖의 실패). 복원은 마이그레이션으로 표를 만든 뒤 같은 이름의 `.copy` 파일을 `COPY ... FROM`으로 넣는다(`docs/runbook.md`).
- **요청 본문 상한**: 본문을 받는 모든 경로를 `Exposure.routes[].max_body_bytes`=65536(64 KiB)으로 선언하고 코드(`Route.max_body`)가 같은 값을 쓴다. 가장 큰 본문은 발화 1000자(한글 3바이트로 약 3 KB)와 봉투인 턴 요청이고 나머지는 훨씬 작다. 값은 이 한도의 여유를 두고 정한 것이며 측정하지 않았다.
- **잡 시간 상한**(`timeout_seconds`): `session-purge` 600초, `backup` 1800초. 둘 다 측정하지 않은 시작값이다(보존 기간이 지난 세션 삭제와 덤프 업로드의 최악을 가정해 여유를 크게 잡았다). 넘기면 deploy가 잡을 멈추고 그 실행은 실패다.

## 왜
- restic: 백업 저장소 프로토콜이 계약에 restic REST로 정해져 있고 restic이 그 표준 클라이언트다. 이미지에는 배포판 패키지로 넣는다.
- COPY·SQLite 백업 API: 실행 중인 DB를 일관되게 꺼내는 엔진의 표준 방법이다. `pg_dump`는 서버 주 버전 이상이어야 하는데 이미지 배포판의 클라이언트 버전이 서버와 어긋날 수 있어 쓰지 않았다(psycopg는 이미 의존).
- 본문 64 KiB: 공개 입구와 영역 게이트웨이가 이 값으로 413을 내므로(계약), 앱이 받을 수 있는 크기와 같아야 한다.

## 검토한 대안과 버리는 이유
- pg_dump 사용: 위 이유. 
- 파일 복사(SQLite): 쓰는 중의 페이지가 섞인다.
- 선언 없이 기본 8 MiB: 발화 서비스에 비해 너무 크다.

## 결과
얻는 것: 데이터를 영역이 스스로 백업하고 복원 절차가 문서에 있다. 감수하는 것: 이미지에 restic이 들어간다(이미지가 커진다). PostgreSQL 쪽 백업은 실제 서버에 대한 시험이 아니라 가짜 실행기로 시험한다(우리 코드만 시험한다).

## 되돌리는 조건
platform이 백업 저장소 프로토콜을 바꾸거나, 영역이 다른 DB 엔진으로 옮길 때.
