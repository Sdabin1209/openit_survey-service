# ADR-0004: HTTP 서버는 표준 라이브러리 ThreadingHTTPServer이고 한계를 문서화한다

## 상태
승인(설계 당시부터), 한계는 측정·방어로 보완(ADR-0018)

## 맥락
서비스가 열어야 하는 엔드포인트는 JSON API 열두어 개와 SSE이고, 이미지는 최소 의존으로 유지하며, 영역은 비밀·접속 문자열을 다루므로 의존을 늘릴수록 공급망 위험이 커진다.

## 결정
`http.server.ThreadingHTTPServer` 하위 클래스(`_Server`)를 쓴다. 요청마다 스레드를 만들고, 비데몬 스레드와 `block_on_close`로 우아한 종료를 한다. 접속 대기열 128, 동시 접속 상한, 소켓 읽기 제한을 직접 둔다.

## 왜 (따른 표준과 근거)
표준: 최소 의존(표준 라이브러리), 서비스 앞단에 gateway가 TLS·속도 제한을 맡는 구조(deploy 소관). 근거 출처: 부하 측정(boundary.md §6-1)이 이 구조에서 요청당 스레드, N=100에서 약 200개 서버 스레드, 메모리 +100~160MB를 확인했다.

## 검토한 대안과 버리는 이유
FastAPI/uvicorn(ASGI), Flask+gunicorn: 비동기·워커 모델과 성숙한 서버 방어를 얻지만 의존이 늘고, 병목이 CPU(파이썬 GIL)라 프레임워크만으로는 처리량이 늘지 않는다고 측정했다(복제로 확장). 이 결정은 '왜 지금 바꾸지 않는가'의 근거일 뿐이고, 프로덕션 서버(gunicorn 등)를 쓰는 것이 표준이라는 점은 인정한다.

## 결과
얻는 것: 의존 없음, 동작을 코드로 전부 읽을 수 있음. 감수하는 것: slowloris·접속 폭주 방어를 직접 구현해야 한다(ADR-0018), HTTP/1.0 요청당 연결, HEAD/OPTIONS 등 미구현.

## 되돌리는 조건
동시 접속 요구가 단일 프로세스의 한계를 넘거나, 서버 방어를 직접 유지하는 비용이 프레임워크 도입 비용을 넘을 때. 검토 대상: 프로덕션 WSGI/ASGI 서버로 바꾸기.
