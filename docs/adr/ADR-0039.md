# ADR-0039: setup-env.sh는 마지막 출력 줄에 SetupEnvReport를 낸다 (U43)

## 상태
승인(헤드 결정 U43, 계약 boundary-contracts 2.6.0, 구조 규칙 1).

## 맥락
deploy가 이 영역의 `.venv/bin/python` 경로와 시험 명령(pytest)을 짐작했다(doctor.sh, check_all.py). 영역 내부 구조를 deploy가 아는 것은 규칙 1 위반이다.

## 결정
`scripts/setup-env.sh`(멱등, 인자 없음, 비밀 없음)가 **표준 출력 마지막 줄**에 계약 `SetupEnvReport` JSON 한 줄을 낸다: `{area: "survey-service", status: ok|fail, exit_code, seconds, environment: {kind: "python-venv", path: ".venv", test_command: [".venv/bin/python", "-m", "pytest"]}}`. 진행 기록(pip 출력 포함)은 모두 표준 오류로 보낸다(스크립트 첫머리에서 표준 출력을 표준 오류로 돌리고 보고만 따로 연 3번 파일 기술자로 낸다). 보고는 종료할 때 한 번 내며(`trap EXIT`) 실패해도 `status: fail`과 종료 코드를 낸다. `test_command`는 리포 루트에서 셸 없이 실행하는 argv이고, `pyproject.toml`의 `addopts = "-q"`가 이미 있어 `-q`를 더하지 않는다(더하면 요약 줄이 사라진다: 측정). 계약 고정은 v2.6.0.

## 왜
계약 2.6.0 SetupEnvReport의 정의를 따랐다. 경로와 시험 명령은 영역이 선언하므로 deploy가 짐작하지 않는다. 진행 기록을 표준 오류로 옮기는 이유는 마지막 줄만이 아니라 표준 출력 전체를 한 줄 보고로 지켜 deploy가 파싱할 때 다른 줄에 흔들리지 않게 하기 위해서다.

## 검토한 대안과 버리는 이유
보고를 별도 파일로 쓰기: 계약이 표준 출력 마지막 줄로 정했다. 성공일 때만 보고하기: 실패의 종료 코드와 소요 시간을 deploy가 요약표에 쓴다.

## 결과
얻는 것: deploy가 이 영역의 환경 경로·시험 도구를 모른다. 감수하는 것: 시험(`tests/test_setup_env_report.py`)은 시험이 도는 환경을 지우고 다시 깔지 않으려고 핀 없는 최소 리포 사본에서 스크립트를 돌린다. 실제 리포의 전체 설치와 `test_command` 전체 실행은 사람이 따로 한다(보고에 기록).

## 되돌리는 조건
계약의 SetupEnvReport 형식이 바뀌면 따른다.
