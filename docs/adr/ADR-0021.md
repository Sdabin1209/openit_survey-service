# ADR-0021: 직원 호출 재알림·실패 기록의 간격 30초·상한 10회와 저장 방식 (CR-H001)

## 상태
승인(헤드가 계약 2.1.0으로 채택). 값은 **측정하지 않았다**.

## 맥락
위험 정지·직원 호출 때 알림이 저장돼도 전달 경로가 하나도 없으면 `staff_alert=DELIVERY_FAILED`이고, 키오스크가 서버에 다시 부르라고 하거나 "직접 알렸는지"를 남길 길이 없었다. 계약 `PUBLIC_API.md` G절이 `POST /v1/sessions/{id}/staff-call/retry`와 `.../report`를 정했다. 계약은 간격·상한의 값을 서비스 설정으로 두고 기본 권고(30초, 세션당 10회)만 적었다.

## 결정
- 설정 `SURVEY_STAFF_CALL_RETRY_MIN_INTERVAL_SECONDS` 기본 **30**, `SURVEY_STAFF_CALL_RETRY_MAX_PER_SESSION` 기본 **10**. 0이면 간격 없음/재알림 불가.
- 간격은 **재알림과 재알림 사이**에만 적용한다. 첫 재알림은 바로 된다(최초 전달이 실패한 직후 키오스크가 누르는 것을 30초 막지 않는다).
- 같은 `turn_id`는 저장된 응답을 그대로 돌려주고 간격·상한을 다시 보지 않는다(멱등). 시도 횟수도 늘지 않는다.
- 재알림은 알림을 새로 만들지 않고 같은 `alert_id`로 **새 SSE 이벤트 행**(새 이벤트 순번)을 쓰고 구독자·웹 푸시에 보낸다. Last-Event-ID로 이어 받는 콘솔도 받는다.
- 상태는 알림 행(`delivery_attempts`, `last_delivery_status`, `last_retry_at`, `manual_notice_*`)과 `staff_call_actions`(세션, turn_id, 동작 -> 응답) 표에 둔다. 재알림 상한은 이 표의 retry 행 수로 센다.
- 실패 기록은 알림의 `manual_notice_*` 갱신, 멱등 행, **접근 기록(staff_access_log, outcome `STAFF_CALL_REPORT`)을 한 트랜잭션**으로 쓴다. 접근 기록이 안 남으면 보고도 남지 않는다(503). 같은 turn_id에 다른 outcome은 409. 보고는 직원이 이미 해결한 알림에도 마지막 알림에 남긴다.
- 권한: 키오스크 역할, 기기 토큰이면 세션을 만든 기기만(`_device_denied`, ADR-0016). 본문은 계약의 엄격한 스키마(`StaffCallRetryRequest`, `StaffCallReport`)로 검증하고 자유 문장·발화 필드는 받지 않는다.
- 재알림의 "확인 -> 전달 -> 기록"은 프로세스 안 락 하나로 직렬화한다.

## 왜
- 30초/10회는 계약 PUBLIC_API G절의 기본 권고이고 그 문서가 "측정하지 않은 자리 표시값, 현장 흐름 자료 없음"이라고 적었다. 서비스도 측정하지 않았다. 표준이 있는 값이 아니다(과다 요청 제한의 일반 관행인 `429 + Retry-After`만 따랐다: RFC 6585 4절, RFC 9110 10.2.3). 간격이 너무 짧으면 구독자·푸시 서비스를 두드리고(푸시 접수 대기 최대 `push_timeout` 3초), 너무 길면 환자 안전 호출이 늦다. 현장에서 직원이 오기까지의 시간 자료가 생기면 설정만 바꾼다.
- 기록과 전달 순서: 먼저 시도 횟수와 이벤트 행을 쓰고(begin) 전달한 뒤 결과를 쓴다(finish). 전달 중 DB 쓰기 잠금을 쥐지 않기 위해서다. 한 트랜잭션으로 묶으면 웹 푸시 접수 대기(최대 3초) 동안 알림 DB의 쓰기 잠금을 쥐어 **새 위험 알림 생성이 그만큼 막힌다**. 환자 안전 경로를 막는 쪽이라 묶지 않았다. 반대로 전달 후 한 번에 쓰면 이벤트 순번을 전달 전에 알 수 없어 SSE 이어 받기가 깨진다.
- 락을 프로세스 안에 둔 이유: 이 서비스는 SSE 허브와 푸시가 이미 한 프로세스 안이다(ADR-0004, 0010). 여러 프로세스로 나눠 띄우면 간격 검사가 서로 못 막는다.
- 접근 기록과 같은 트랜잭션: 감사 기록 없는 환자 관련 기록을 만들지 않는 기존 원칙(D88)을 따른다.
- 첫 재알림 즉시 허용: 계약은 간격 위반만 429로 정한다. 최초 실패 직후를 막는 것은 임상 근거가 없다.

## 검토한 대안과 버리는 이유
- 서버가 스스로 재전송(큐): 살아 있는 구독자가 없으면 닿지 않고 키오스크가 시작할 방법이 여전히 없다(CR-H001 4절). 후속.
- 상한을 알림 행의 시도 횟수로 세기: 최초 전달·위험 신호 경로의 재전송과 섞여 "재알림 몇 번"이 불분명하다. 동작 표로 센다.
- 지수 백오프로 간격 증가: 측정 없는 복잡도. 계약도 고정 `retry_after_s`다.
- DB 잠금으로 간격 검사(여러 프로세스 대응): 지금 배포 형태(한 프로세스)에 없는 요구라 하지 않는다.

## 결과
얻는 것: 키오스크가 전달 실패를 만회하고, 직원 콘솔이 전달 실패 알림과 수동 통지 결과를 구분하고, `/readyz`의 `staff_alerts`에 재알림 건수가 나온다(`staff_call_retries`, `..._delivered`, `..._failed`, `..._replayed`, `..._rejected_interval`, `..._rejected_limit`, `..._no_open_alert`, `staff_call_reports`, `..._not_notified`).
감수하는 것:
- **크래시 구간**: begin 뒤 finish 전에 프로세스가 죽으면 시도 횟수는 올랐는데 turn_id 응답은 저장되지 않아, 같은 turn_id 재전송이 시도를 한 번 더 센다(그리고 한 번 더 보낸다). 더 보내는 안전한 방향이고 상한 10회가 막는다. 시험이 이 구간을 모사한다(`test_crash_between_begin_and_finish...`).
- 값은 측정하지 않았다. 간격이 현장에 안 맞을 수 있다.
- 한 프로세스 가정.
- 상한 초과도 간격 같은 429이며 `details.reason: RETRY_LIMIT`로 구분한다. `Retry-After`는 간격 값이지만 상한은 기다려도 풀리지 않는다.

## 되돌리는 조건
현장 자료가 생기면 값을 바꾼다(코드 변경 없음). 여러 프로세스로 확장하면 간격 검사를 DB 행 잠금(`SELECT ... FOR UPDATE`)으로 옮기고 이 ADR을 대체한다.
