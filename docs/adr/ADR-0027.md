# ADR-0027: /readyz 응답 전체에 총 마감 하나, 보조 수치는 확인과 동시에 읽고 짧은 유예만 기다린다

Supersedes: [ADR-0011](ADR-0011.md)의 /readyz 부분(DB 확인 총 마감). 접속·문장 timeout과 재접속 유예는 ADR-0011 그대로다.

## 상태
승인(헤드 지시 wo-readyz, 2026-10-29). 유예 값은 측정하지 않았다.

## 맥락
계약 FAULT_POLICY 5: 의존이 응답하지 않으면 /readyz는 2초 안에 503(E2E 단언 허용 2.5초). gpu-dev E2E 5pn(PostgreSQL을 `docker network disconnect`)에서 503이 2.8초에 왔다(계약 2.2.0 열차, main b31ef4e; 03:00 실행 122dfb9는 통과).
코드를 읽으면 이전 `readiness()`는 (1) 세 저장소 확인(동시, 총 2.0초) 뒤에 (2) 보조 수치(outbox 건수·알림 상태, **주 연결**)를 1.0초까지 **이어서** 기다렸다. 최악 한 응답은 2.0+1.0=3.0초다. 확인이 늦게 통과(예: 1.5초)하고 주 연결 읽기가 매달리면 2.5초가 되는 것을 시험으로 재현했다(`tests/test_readyz_total_budget.py`, 수정 전 2.50초).
네트워크 분리에서는 패킷이 사라지므로 새 연결(확인)은 libpq `connect_timeout`(2초)까지, 이미 열린 주 연결은 문장 상한(2초)+1초 강제 끊기까지 걸린다. 분리 직전에 시작한 요청은 확인이 통과한 뒤 보조 수치에서 1초를 쓰고 200을 내고, 다음 요청이 확인에서 2초를 써 503을 낸다. 분리 시점부터 503까지 약 3초다. 2.8초 관찰과 맞는 경로다. **gpu-dev에서 이 경로가 실제 원인인지는 재현하지 않았다**(로그를 보지 못했다).

## 결정
- 세 확인과 보조 수치 읽기를 **동시에** 시작하고, 확인은 총 마감 `SURVEY_READYZ_DB_TIMEOUT_SECONDS`(기본 2.0) 안에 끝난 것만 통과로 센다.
- 보조 수치는 확인이 끝난 뒤 `STATS_GRACE_S`(0.2초)만 더 기다린다(총 마감 안). 못 읽으면 마지막 값에 `db_stats_stale=true`. 확인이 하나라도 실패하면 보조 수치는 쓰지 않는다.
- 응답 한 번의 최악은 총 마감(2.0초)이다. 분리 직전 요청(확인 통과)은 확인 시간 + 0.2초 안에 끝난다.

## 왜
- 계약 FAULT_POLICY 5의 2초는 응답 하나의 상한이므로 마감을 응답 전체에 하나만 둔다(호출별 상한의 합이 아니라 전체 마감: ADR-0008과 같은 원칙).
- 보조 수치는 관측용이고 준비 판정에 쓰지 않는다. 그래서 판정을 늦추면 안 된다.
- 0.2초 유예는 측정하지 않았다. 정상 보조 수치는 로컬 질의 몇 ms라 넉넉하다는 판단이다. 너무 짧으면 정상일 때도 stale이 자주 나온다(시험 `test_healthy_readyz_still_reads_fresh_stats`가 이 PC에서 fresh를 확인).

## 검토한 대안과 버리는 이유
- 보조 수치를 마감까지 기다리기(동시 시작, 마감 하나): 응답 하나는 2초 안이지만 분리 직전 요청이 2초를 다 써서 다음 503이 최대 4초 뒤가 된다.
- 보조 수치를 /readyz에서 빼고 백그라운드 주기로 갱신: 더 깔끔하나 스레드가 하나 늘고 응답 모양의 의미(언제 값인지)가 바뀐다. 다음에 검토.
- 확인 총 마감을 줄이기(예: 1.5초): libpq `connect_timeout`은 2초 미만이 의미 없다(ADR-0011).

## 결과
얻는 것: 응답 하나의 최악 2.0초(+스레드 여유), 분리 직후 요청은 확인 시간 + 0.2초. 감수하는 것: 분리부터 503까지는 여전히 "진행 중 요청 + 다음 요청의 확인 2초"라서 최악 약 2.2초 + 폴링 간격이다. 이 값이 E2E 단언(2.5초)을 언제나 넘지 않는다고 보장하지 못한다(E2E가 시간을 어떻게 재는지는 deploy 쪽, 미확인). 보조 수치가 가끔 stale일 수 있다.

## 되돌리는 조건
보조 수치를 백그라운드 갱신으로 옮기면 유예가 필요 없어진다. E2E에서 여전히 넘으면 측정값으로 다시 정한다.
