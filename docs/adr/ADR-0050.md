# ADR-0050: 시계 주입(턴 마감, /readyz 마감, 추론 재시도 예산)

## 상태
승인(헤드 지시 U422, 2026-10-31). 와이어 형식·HTTP 응답·잡 출력은 바뀌지 않는다.

## 맥락
시험이 실제 시간을 기다리거나 재면 합격·불합격이 기계가 바쁜 정도에 따라 갈린다(check-all 동시 실행에서 2.42초 같은 값이 나와 "2초에 끊긴다" 시험이 실패했다). 이 영역의 시간은 둘로 나뉜다: (1) 우리가 정한 마감·예산(턴 총 마감 9초, /readyz 확인 마감, 추론 재시도 예산, 푸시 발송 마감), (2) 라이브러리 안의 시간(waitress 연결 시한, PostgreSQL statement_timeout, 소켓 읽기 시한). (2)는 우리가 시험할 대상이 아니다.

## 결정
- (1)은 시계를 인자로 받는다: `Orchestrator(clock=)`, `TurnCtx(clock)`, `App(clock=)`, `RemoteInference/RemoteModelSession(monotonic=, sleep=)`, `AlertService(monotonic=)`. 기본값은 실제 시계(`time.monotonic`, `time.sleep`)이고 wiring(App)이 하나를 모든 곳에 넘긴다. `PublicApi`는 오케스트레이터의 시계를 쓴다.
- 블로킹 대기는 `wiring/clock.join_until(thread, until, now)`로 한다: 0.05초 조각으로 `thread.join`하며 매번 주입한 시계로 마감을 확인한다. 실제 시계에서는 원래 `join(timeout)`과 같고, 가짜 시계에서는 시험이 `advance()`할 때 마감이 난다.
- 시험은 `tests/timing.py`의 `FakeClock`을 넣고 시간을 직접 흘린다. 판정은 결과(NOT_COMMITTED, 503과 사유, 재시도 여부)다. 실제로 기다리는 시간은 0이다.
- (2)는 시험하지 않는다: 넘기는 값(waitress `channel_timeout`·`connection_limit`·`threads`, PostgreSQL 접속·문장 시한, 호출별 추론 상한)이 설정에서 오는지 확인하고, 가짜 의존이 즉시 던지는 시간 초과·연결 거부에 대한 우리 처리(오류 종류, 상태 코드, 재시도 여부)를 본다.
- 시험이 자기 가짜의 신호를 기다리는 대기(Event.wait, join, wait_until)는 매달림 감시이고 숫자는 `tests/timing.py`의 `HANG_GUARD_SECONDS = 300` 하나다.

## 왜
- 표준: 의존성 주입(시계를 인자로 받는 것은 시험 가능한 시간 코드의 관행). 마감을 계산하는 시점을 스레드 시작 앞으로 옮겼다(시작 뒤에 정하면 시계가 그 사이 흘러 마감이 밀린다).
- 대안과 버리는 이유: 전역 `time` 패치(freezegun 등)는 `Thread.join(timeout)`·`Event.wait(timeout)`·소켓 timeout 같은 블로킹 대기를 움직이지 못한다. 시험에서 시한을 늘리는 방법은 덜 깨질 뿐 판정이 시간에 기대는 것은 그대로다.

## 결과
얻는 것: 시간 시험이 부하와 무관하게 같은 결과를 낸다. 감수하는 것: 시계를 받는 인자가 늘었고(기본값이 있어 호출부는 그대로), `join_until`이 0.05초 간격으로 마감을 확인한다(측정하지 않았다).
컴포넌트 코드에는 `import time`도 `survey_service.config`(실제 시계) import도 `threading.Timer`도 없다(tests/test_structure.py::test_components_never_read_the_time_module_or_the_real_clock_config가 강제한다). 시계(`clock=`, `monotonic=`), `sleep=`, 주기 대기(`wait=`), 시한 타이머(`configure(timer=)`)는 모두 **필수 인자**이고 기본값이 없다(컴포넌트가 config의 기본 시계를 끌어오면 숨은 의존이다: D104 4번).
wiring(App, db.open_stores, purge_job)과 진입점(cli)이 `survey_service/config.py`의 실제 값(`REAL_WALL_CLOCK`, `REAL_MONOTONIC`, `REAL_SLEEP`, `real_wait`, `real_timer`)을 명시적으로 넘긴다. 시험은 `tests/timing.py`의 `fake_clock()`·`clock_kwargs()`·`FakeWait`·`FakeTimer`를 넘기고, PgConn에는 conftest의 자동 픽스처가 가짜 단조 시계와 `FakeTimer`를 `session_store.configure`로 넣는다.
주입한 것: PgConn 재접속 유예(`configure(monotonic=)`)와 문장 강제 끊기 타이머(`configure(timer=)`), 내보내기 스레드의 주기 대기(`TraceExporter(wait=)`), `retention_purge.purge(now)`(호출자가 `clock()`을 넘긴다), 저장소·알림 저장소·전송기·봉투 만들기·로더의 기록 시각(`clock`), 푸시 마감(`monotonic`), 추론 클라이언트(`monotonic`, `sleep`).
남은 것: 진입점 `server.py`의 SSE 하트비트와 `close_server` 기다림(진입점이라 직접 읽는다; 하트비트 주기 값은 설정에서 온다), wiring의 백그라운드 루프(`Event.wait`: 컴포넌트가 아니다).

## 되돌리는 조건
조각 간격이 CPU를 눈에 띄게 쓰면(측정 필요) 이벤트 기반 대기로 바꾼다.

## 추가(wo-433): 계약 검증기는 기동 때 한 번 만든다
`boundary_contracts.validator()`는 호출마다 스키마 파일을 다시 읽고 검사한다. `/readyz`가 요청마다 만들면 2초 마감 뒤에 그 비용이 붙어(E2E 5pn 2.9초 관찰) 마감이 어긋난다. 그래서 `SurveyReadyz`(App), `StaffPushPayload`(AlertService), `QuestionBank`(ReleaseLoader, 정수 버전별)는 한 번 만들어 재사용한다. 비용은 측정하지 않았다. 시험: tests/test_validators_built_once.py.
