# ADR-0010: 직원 알림 스트림은 SSE이다(WebSocket 아님)

## 상태
승인(D64, PUBLIC_API.md)

## 맥락
알림은 서버에서 직원 콘솔로 가는 단방향 이벤트이고, 놓친 알림은 목록 API로 따라잡을 수 있어야 한다.

## 결정
`GET /v1/staff/alerts/stream`(SSE). 이벤트 `alert`·`resolved`에 순번 `id:`를 붙여 `Last-Event-ID`로 이어 받는다. 재연결 불가 구간은 `resync`, 연결 확인은 `heartbeat`(CR-016), 연결 상한(`SURVEY_MAX_SSE_CONNECTIONS`).

## 왜 (따른 표준과 근거)
표준: 서버 푸시 단방향에는 SSE(자동 재연결, Last-Event-ID가 표준 기능), 브라우저 EventSource가 지원. 근거 출처: DECISIONS.md D64, PUBLIC_API.md 43행, docs/design.md §알림, kiosk-frontend CR-004(주석 줄을 앱 코드에서 볼 수 없어 이름 있는 하트비트를 요청).

## 검토한 대안과 버리는 이유
WebSocket: 양방향이 필요 없고 HTTP 프록시·재연결·이어받기를 직접 구현해야 한다. 폴링만: 지연이 길고 알림 도달이 늦다(목록 API는 보충 수단으로 유지). 웹 푸시는 병행한다(D64).

## 결과
얻는 것: 단순한 단방향 스트림, 표준 재개. 감수하는 것: 연결마다 스레드 하나(상한 필요), 일부 프록시의 버퍼링(`X-Accel-Buffering: no` 사용).

## 되돌리는 조건
양방향 실시간 통신(직원이 서버로 실시간 명령)이 필요해지거나 연결 수가 스레드 모델의 한계를 넘을 때.
