# ADR-0054: 되묻기 한도 뒤에는 직원을 부르지 않고 그 문항을 빈칸으로 두고 다음 문항으로 간다 (U36·G12·U35)

Supersedes: ADR-0020, ADR-0032의 "한도 뒤 동작"(직원 호출·정지). 상한 값 3과 연속 판정 규칙은 그대로다.

## 상태
승인(사용자 결정, 2026-11-03).

## 맥락
ADR-0020은 REASK·CONFIRM(ADR-0032에서 REDIRECT와 추출·검증 실패 턴도)이 연속 N=3번 나온 뒤 또 나오면 정지(`PAUSED_RISK`, 사유 `REASK_LIMIT`)와 `CALL_STAFF` 알림으로 직원을 불렀다. 키오스크가 위험 정지와 구분하지 못한다는 한계(G12)가 있었고, 사용자가 동작을 바꾸기로 했다: 직원 호출이 아니라 그 칸을 빈칸으로 두고 다음으로 간다.

## 결정
- 한도에 닿은 턴(`SURVEY_MAX_CONSECUTIVE_REASK`, 기본 3, 0이면 끔, 문항 세트 저작 한도와의 최솟값은 ADR-0014 그대로)은 서비스가 A 출력을 합성 `SKIP`(사유 `REQUEST_SKIP`)으로 바꿔 쓴다: 현재 문항을 건너뛴 문항으로 기록하고 `current_question_id`를 문항 순서표·건너뛰기 표의 다음 문항(마지막이면 `END`, 세션 종료)으로 옮긴다(`FlowTable.next_after`, `TurnGraph._reask_blank`). 이번 턴에 저장되는 값(`save=true`)은 그대로 저장한다. 응답 문장은 다음 문항을 묻는 일반 응답(LoRA-B)이다.
- 세션은 정지하지 않고 알림도 만들지 않는다. 직원 호출 경로(정지 사유 `REASK_LIMIT`, `CALL_STAFF` 알림, 상태 `pause_reason`)는 이 사유로는 더 쓰지 않는다. 설정으로 남기지 않는다(사용자 결정은 스킵이다).
- 빈칸 사유: 진행 기록의 건너뛴 문항 사유에 `REASK_LIMIT`를 더하고(`SessionStore`·`TurnTrace`·`DispatchInput`의 `SkipReason`), 결과 조회 `SessionResult.skipped_details[].reason`에 `REASK_LIMIT`를 더한다. 그 문항의 값 없는 칸은 UNCLEAR 대신 `REASK_LIMIT`로 나온다(`blank_details`). 문진 스키마 정수 버전은 1 그대로다(같은 정수 안의 추가, 계약 CONVENTIONS 12절; `schema/CHANGELOG.md`).
- 연속 판정은 합성 `SKIP`이 끊는다(SKIP은 연속으로 세는 action이 아니다). 다음 문항에서 다시 센다.
- 순서표에 없는 문항이면(다음을 알 수 없다) 건너뛰지 않고 되묻기를 그대로 둔다.

## 왜
- 사용자 결정(U36·G12·U35)이 근거다. 환자가 같은 질문을 계속 받는 것을 끊고, 직원 호출 없이 문진을 이어 가며, 무엇이 왜 빈칸인지는 결과에 남긴다(U35).
- 다음 문항을 서비스가 정하는 이유: A 출력의 `next_item`은 REASK에서 현재 문항이다(계약 ActionExtraction). 서비스가 쓰는 표(`QuestionFlow`)는 서비스 소유이고 이미 A 입력 state 조립에 쓴다. 이웃 영역 구조를 새로 알지 않는다.
- 합성 출력에 `SKIP`을 쓴 이유: 응답 모델(LoRA-B)은 `SKIP`을 "이 문항은 넘어가고 다음 문항을 묻는다"로 학습한 입력 형태가 있다(`response_request.py`의 HOLD·SKIP 분기). 새 action을 만들면 계약 밖이다. 사유 `REQUEST_SKIP`은 환자가 요청하지 않았는데 그렇게 부르는 것이라 정확하지 않다. **B 모델이 이 합성 입력에 어떤 문장을 내는지는 확인하지 못했다(GPU·학습 쪽, 추정).**
- 진행 기록의 사유를 `REQUEST_SKIP`이 아닌 `REASK_LIMIT`로 두는 이유: 결과 조회에서 거절(REJECTED)과 한도를 구분해야 한다(U35의 목적).

## 검토한 대안과 버리는 이유
- 직원 호출 유지 + 설정 스위치: 사용자 결정이 스킵이고 두 경로를 유지하면 시험과 문서가 갈린다.
- 빈칸 사유를 기존 `UNCLEAR`로 쓰기: 한도에 닿았다는 사실이 사라진다(U35의 구분).
- `SessionResult`에 새 필드: 기존 `skipped_details`에 enum 값 하나가 같은 뜻이고 읽는 쪽 변경이 가장 작다.

## 결과
얻는 것: 환자가 막히지 않고 직원 호출 알림이 줄어든다. 결과에 한도 빈칸이 보인다. 감수하는 것:
- 같은 정수 버전 안에서 enum 값이 늘었다. **읽는 쪽이 enum을 닫힌 집합으로 검증하면(ops-feedback의 TurnTrace 읽기, 병원 시스템의 결과 읽기) 새 값을 거부할 수 있다.** CONVENTIONS 12절은 enum 축소만 깨지는 변경으로 보고 추가는 허용한다. 읽는 쪽 점검은 헤드·해당 영역 몫이다(`schema/CHANGELOG.md`에 적었다).
- 키오스크·프론트가 `pause_reason=REASK_LIMIT`를 더는 받지 않는다. 계약의 enum 값은 지우지 않았다(좁히면 깨지는 변경이다). 이웃 계약 문서(PUBLIC_API.md 등)가 이 사유를 말하는 부분은 헤드가 고친다.
- 환자가 말하지 못한 값이 빈칸이 된다: 임상 의미는 병원이 결과에서 판단한다(`skipped_details`).

## 되돌리는 조건
사용자가 한도 뒤 동작을 다시 정할 때.
