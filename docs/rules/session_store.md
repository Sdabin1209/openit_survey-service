## 9-2. Session Store 반영 효과

| 동작 | 현재값 | 이력 | 확인 대기 | 위험 표시 | 왜 |
|---|---|---|---|---|---|
| 첫 저장 | 답(값) | 그대로 | 그대로 | 받은 것 | B1. |
| 새 revision | 답(값) | 이전 답이 있으면 추가 | 그대로 | 받은 것 | C1. 이전 답은 수정 이력으로 넘긴다. |
| 모름 기록 | 모름 | 이전 답이 있으면 추가 | 그대로 | 없음 | B7. "이전 답"은 현재값이 값인 경우만이다. 모름·거절은 답이 아니라 이력에 쌓지 않는다(LoRA-A 입력의 답한 슬롯 목록도 같은 기준이다). |
| 거절 기록 | 거절 | 이전 답이 있으면 추가 | 그대로 | 없음 | B8. |

| 무효화 | 없음 | 이전 답이 있으면 추가 | 없음 | 없음 | C2. |

**갱신·생성별 변화**

1. 진행 기록 갱신.직전 응답 지시 → 교체. 열린 요청 → 통째로 교체. 건너뜀 추가 → 같은 문항이 있으면 사유 교체, 없으면 추가. 건너뜀 해제 → 뺀다(추가와 해제가 함께면 해제 먼저). 확인 중단 추가 → 추가. 확인 중단 해제 → 뺀다. 세션 상태 → 값이 오면 교체. 중지 이력 추가 → 끝에 추가. Plan 기록 갱신 → 통째로 교체.
   - 왜: 저장소가 판단 없이 반영하도록 효과를 하나로 정한다. 확인 중단을 빼는 것도 진행 기록을 쓰는 유일한 쪽인 Plan이 정한다(원칙 6).
2. 세션 정보 생성 → 세션 정보를 만들고, 응답 기록은 비우고(모든 슬롯 없음), 진행 기록은 {직전 응답 지시 없음, 열린 요청 {빈 목록, 아니요, 빈 목록}, 건너뜀·확인 중단 빈 목록, 진행 중, 중지 이력 빈 목록}, Plan 기록은 {빈 목록들, 0}, 대화 로그·전달 기록은 빈 목록.
   - 왜: 초기값이 정해져 있어야 첫 턴이 다른 턴과 같은 규칙으로 돈다.

## 정밀도와 근거의 보존

현재 답과 확인 대기 후보에 확보된 value_metadata는 해당 값과 함께 보존한다. 이전 값에 메타데이터가 있으면 history의 {value, value_metadata} 항목으로 표현하고, 미수집 이력에 정밀도나 근거를 임의 생성하지 않는다. 조회·저장 포트는 아직 데이터 계약 초안이며 자료형의 제안 범위는 contracts/proposals.yaml에 기록한다. 실제 API 채택·전송·재시도 방식은 구현 담당자의 책임이다.
